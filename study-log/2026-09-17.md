## 1. 오늘 한 일

**어제 vs 오늘**
- 어제: SSH terminal → Flask development server (reboot 후 자동 실행 안 됨)
- 오늘: systemd → Gunicorn → Flask (SSH 종료·reboot 후에도 유지)

**흐름**
1. EC2 Start → SSH 재접속 → mongod는 enabled, active인데 5000 port를 listen하는 Flask process는 없음
   → systemd가 관리하는 MongoDB는 boot 후 다시 켜지지만, 어제 terminal에서 직접 켠 Flask는 안 켜진다는 차이 확인
2. 기존 venv 활성화 → Gunicorn 설치 → 실행 실패 해결(3-② 참고) → `gunicorn --bind 0.0.0.0:5000 app2:app`로 Windows browser 외부 접속 성공
3. `flask-study.service` 작성 → `daemon-reload → start → enable` → active, enabled 확인
4. SSH 종료 후에도 페이지 동작, reboot 후에도 Gunicorn과 Flask 자동 실행 확인
5. reboot 중 MongoDB failed → 복구(3-③ 참고)

## 2. 핵심 개념

**process / service**
- program → disk에 저장된 실행 가능한 코드
- process → program이 지금 실행 중인 instance
- service → systemd가 설정대로 관리하는 장기 실행 process
- 설치되어 있는 것 ≠ 실제로 실행 중인 것

**systemd / systemctl**
- systemd → service/process를 관리하는 system/service manager
- systemctl → systemd에 start, stop, status, enable 명령을 내리는 command
- active = 지금 실행 중 / enabled = boot 시 자동 시작 → **start와 enable은 별개**

**Gunicorn**
- Flask application을 실행하는 WSGI server
- `app2:app` → `app2.py` module 안의 `app` Flask application object

**작업 위치와 network**
- EC2 Public IPv4 → 내가 접속할 EC2의 목적지 주소
- My IP → Security Group에서 접속을 허용할 내 쪽 공인 IP
- SSH: local WSL → EC2 Public IPv4:22 → remote EC2
- prompt로 구분: `jhk-franciscus@DESKTOP-...` = local WSL / `ubuntu@ip-172-31-...` = remote EC2
- `uname -r`도 실행한 곳의 kernel을 보여주니까 WSL과 EC2 결과가 다르다

## 3. 막힌 점 → 원인 → 해결

**① 접속 단계 — SSH Connection timed out**
- 원인: Security Group에 SSH 22 inbound rule이 없었다
- 해결: `SSH / TCP / 22 / My IP` rule 추가

**② 실행 환경 단계 — Gunicorn worker 실행 실패**
- 오류: `ModuleNotFoundError: No module named 'flask'`
- 원인: 활성화한 `day0072-f2` venv에 Flask, PyMongo가 없었다
- 해결: 같은 venv에 package 설치 → 실행 성공
- 배운 점: Gunicorn이 Flask application을 실행할 때 필요한 Flask·PyMongo 등의 package를 같은 Python environment에서 사용할 수 있어야 한다.

**③ reboot 단계 — MongoDB failed**
- 확인: `systemctl status` + `journalctl`
- 원인: MongoDB 8.0.32 ↔ 새로 boot된 kernel 7.0.0-1012-aws 호환성 문제
- 해결: 이미 설치되어 있던 6.17.0-1017-aws kernel로 boot → 실습 환경 유지를 위해 6.17을 기본 boot 대상으로 설정 → 다시 reboot
- 결과: mongod active / flask-study active / Gunicorn :5000 LISTEN / browser 정상
- GRUB/kernel 명령 자체는 암기 대상으로 보지 않는다

## 5. 독립성 평가

**진행한 것**
- 어제 한 EC2 생성~첫 외부 CRUD 배포를 반복하지 않고, 다음 단계(Gunicorn + systemd → SSH 종료 후 유지 → reboot 후 자동 시작)까지 진행

**처음에 섞여서 교정 받은 것**
- Public IPv4 vs My IP
- systemd vs Gunicorn 역할
- venv 활성화의 의미
- local WSL vs remote EC2 작업 위치
- → 교정 후 재검증에서 핵심 구분을 다시 맞췄다

**현재 수준**
- 한 번 배포해 본 단계 → service로 운영하고 기본 오류 위치를 추적해 본 단계까지 옴
- 전체 명령과 배포 흐름을 아무것도 안 보고 혼자 재현하는 수준은 아직 아니다

## 면접 부록

**30초 스크립트**
> AWS EC2에 Flask와 MongoDB 프로젝트를 처음 배포한 다음 날, terminal에서 직접 실행하던 Flask를 Gunicorn과 systemd service 구조로 바꿨습니다. 그래서 SSH를 끊어도, 서버를 reboot해도 자동으로 다시 실행되는 것까지 확인했습니다. reboot 과정에서 MongoDB가 failed 상태가 됐는데, systemctl status와 journalctl로 확인해 보니 새로 boot된 kernel과 MongoDB 버전의 호환성 문제였습니다. 이미 설치되어 있던 이전 kernel로 boot해서 복구했고, 이 과정에서 service 상태, log, port, 내부 HTTP, 외부 network 순서로 범위를 좁히는 흐름을 익혔습니다.

**예상 꼬리질문 → 답변 방향**
- start와 enable 차이는? → start는 service를 지금 실행하고, enable은 boot 시 자동 시작하도록 설정한다. 현재 상태 확인에서는 active와 enabled를 각각 확인했다.
- SSH를 끊어도 왜 계속 돌아가나? → Flask를 terminal이 아니라 systemd가 Gunicorn을 통해 관리하기 때문
- MongoDB 문제는 어떻게 찾았나? → systemctl status로 failed 확인, journalctl로 원인 확인
- kernel 문제는 근본 해결인가? → 근본적인 호환성 해결은 아니고, 실습 환경을 유지하기 위해 MongoDB가 정상 동작하는 기존 6.17 kernel을 기본 boot 대상으로 설정한 우회 조치였다.
