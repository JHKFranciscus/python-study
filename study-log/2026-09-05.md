# 공부일지 — Flask + MongoDB + fetch() CRUD

**한 줄 요약**
fetch() → Flask → MongoDB로 이어지는 GET/POST/PATCH/DELETE를 전부 동작시켰고, 막혔던 지점은 문법이 아니라 "지금 이 변수에 뭐가 들어 있는가"를 놓친 데서 나왔다.

**키워드**: fetch, JSON.stringify, request.get_json, jsonify, response.json, ObjectId, dataset, querySelector/All, status code

---

## 1. DOM element와 거기서 꺼낸 value는 다른 것

**막힌 것**
- `querySelector()`가 주는 element 하나와 `querySelectorAll()`이 주는 collection을 혼동했다.
- input element 자체와 `.value`를 구분하지 못했다.

**시도**
- 각 변수에 collection이 들어 있는지 element 하나가 들어 있는지 다시 추적했다.

**배운 것**
- DOM element와 그 element에서 꺼낸 value는 별개의 값이다.
- collection을 순회할 때 callback parameter에는 collection 전체가 아니라 element 하나가 들어온다.

---

## 2. 값은 단계마다 형태가 바뀐다 (browser ↔ Flask ↔ MongoDB)

**막힌 것**
- `JSON.stringify()` 작성에서 오류가 있었다.
- Flask가 반환한 JSON의 key와 JavaScript에서 접근하는 key를 일치시키지 못했다.

**시도**
- browser → Flask → MongoDB → Flask → browser로 데이터가 이동하면서 type과 형태가 어떻게 달라지는지 확인했다.

**배운 것**
- JavaScript object를 request body로 보낼 때는 `JSON.stringify()`, Flask에서 받을 때는 `request.get_json()`을 쓴다.
- Flask는 `jsonify()`로 응답하고, browser는 `response.json()`으로 받는다.
- MongoDB의 `ObjectId`는 JSON response를 위해 string으로 바꾸고, `_id`로 조회할 때는 다시 `ObjectId`로 변환해야 한다.

---

## 3. 상태 변경 버튼에 값을 붙여두고 꺼내 쓰기

**막힌 것**
- 상태 변경 버튼에 필요한 `_id`와 `important` 값을 어떤 식으로 연결할지에서 **교정이 필요했다.**
- `dataset`의 값이 문자열이라는 점과 `let`의 block scope를 실제 상태 변경 코드에 바로 적용하지 못했다.

**시도**
- 버튼의 `data-*` attribute에 필요한 값을 저장하고, event 발생 시 `dataset`으로 꺼내 PATCH와 DELETE 요청에 사용했다.

**배운 것**
- `dataset`을 통해 읽은 값은 문자열이므로 `"true"`와 boolean `true`를 구분해야 한다.

---

## 4. CRUD 후 화면을 DB에 맞추기

**시도**
- 각 CRUD 요청 후 `loadTasks()`를 다시 실행해 최신 DB 데이터를 조회하도록 연결했다.
- 직접 서버를 실행해 조회·등록·상태 변경·삭제가 모두 정상 동작하는 것을 확인했다.

**배운 것**
- CRUD 후 DB의 최신 데이터를 다시 GET해서 DOM을 재생성하면 화면을 DB의 현재 상태와 맞출 수 있다.

---

## 5. CS — status code

- `200`, `201`, `404`, `405`, `500`의 의미와 발생 상황을 구분했다.
- `404`는 path가 없을 때, `405`는 path는 있지만 method를 허용하지 않을 때, `500`은 서버 내부 처리 오류일 때 발생한다.
- 단, 이건 CS 학습으로 정리한 것이지 오늘 실행 중에 직접 만난 것이 아니다. 현재 코드는 status code를 따로 지정하지 않아 정상 응답이 전부 기본 `200`이다. (자세한 건 부록 C)

---

## 직접 한 것 / 교정받은 것

**직접 한 것**
- API의 method와 URL 설계
- 상태 변경 버튼에 `_id`를 연결하고 `querySelectorAll()`과 event callback으로 PATCH 요청을 보내는 큰 구조 작성
- 후반 확인 문제에서 `forEach()` callback parameter, `jsonify()` / `response.json()`, `ObjectId → string → ObjectId`, `request.get_json()` 흐름을 스스로 설명한 것
- 요구사항에 따라 각 CRUD 요청 뒤에 `loadTasks()`를 연결하고 실제 동작을 확인한 것
- 서버를 직접 실행해 조회·등록·상태 변경·삭제가 모두 정상 동작하는 것을 확인한 것

**교정받은 것**
- `querySelector()`의 반환값 판단, `JSON.stringify()` 표기, Flask의 key와 JavaScript의 key 불일치, `important`를 버튼에 보관하는 방식, `dataset` 값 비교, `let`의 block scope
- 전체 CRUD 흐름을 전혀 모른 상태는 아니었지만, 세부 값의 위치·type·scope를 실제 코드에 연결하는 과정에서는 여러 차례 교정이 필요했다.
- 지점별 정확한 경계는 **부록 D**에 정리했다.

## 독립 구현 여부 (확정)

- 오늘 구현만으로 독립 구현 성공 여부는 확인하지 않았다.
- 오늘 메모 CRUD는 요구사항을 단계별로 받고 여러 오류를 교정받아 완성했으므로, **정상 동작했다는 사실과 독립 구현 성공은 구분한다.**
- 같은 메모 CRUD 코드를 다시 작성하는 것만으로는 이미 본 구조를 기억해서 재현하는 것인지 판단하기 어렵다. 실제 독립 구현 여부를 확인하려면 이후 독립 재현 기회에 field 구성, 상태 변경 조건, 화면 구조나 데이터 흐름 등이 다른 문제를 처음부터 설계·구현해 봐야 한다.
- 다만 이 확인을 위해 오늘이나 다음 날의 기존 커리큘럼을 추가·변경하지는 않는다.

---

## 아직 부족한 것

- 개념을 알고 있어도 실제 코드에서 collection/element, DOM/value, 문자열/boolean, scope를 즉시 판단하지 못하는 경우가 있었다.
- HTTP method 자체는 구분하지만, 전체 흐름을 설명하면서 등록 요청을 순간적으로 PATCH라고 잘못 연결한 적이 있다.
- 그래서 문법 암기보다, 지금 변수에 무엇이 들어 있고 그 값이 다음 단계에서 어떤 형태로 바뀌는지 추적하는 능력이 더 필요하다.

# 부록

## A. 30초 면접 스크립트 (말할 때 그대로)

"Flask와 MongoDB, JavaScript의 fetch를 연결해서 메모를 조회·등록·중요 표시·삭제하는 CRUD 웹을 만들었습니다.
막혔던 지점은 대부분 문법이 아니라 지금 이 변수에 무엇이 들어 있는지를 놓친 데서 나왔습니다. 예를 들어 dataset으로 읽은 값은 문자열이라 boolean true와 구분해야 했습니다.
CRUD가 끝날 때마다 다시 GET 요청을 보내 DB의 최신 데이터로 화면을 다시 그려서, 화면과 DB 상태를 일치시켰습니다.
다만 이번 구현은 중간에 여러 부분을 교정받으며 완성한 것이라, 완전히 혼자 구현했다고는 말씀드리지 않겠습니다."

## B. 나올 만한 꼬리질문과 답 방향

- **"이거 혼자 다 하신 건가요?"**
  → API의 method와 URL 설계는 직접 했고 최종 동작도 직접 확인했지만, 실제 구현 과정에서는 상태 변경 버튼의 값 연결을 포함해 여러 부분에서 교정을 받았다고 그대로 말한다. 포장하지 않는다. (지점별 경계는 부록 D)
- **"404랑 405 차이가 뭔가요?"**
  → path가 없으면 404, path는 있는데 그 method를 허용하지 않으면 405.
- **"PATCH를 왜 쓰셨나요?"**
  → 중요 상태만 바꾸는 요청이라 PATCH로 구성했다고 답한다. PUT과의 비교는 오늘 다루지 않았으므로 아는 범위까지만 말한다.
- **"화면 갱신은 어떻게 하셨나요?"**
  → CRUD 후 다시 GET을 보내 최신 데이터로 DOM을 재생성했다고 답한다. 오늘 써본 방식은 이 방법 하나라고 덧붙인다.
- **"dataset에서 왜 문제가 생겼나요?"**
  → 읽어온 값이 문자열 `"true"`인데 boolean으로 다룰 뻔했다고 답한다.

## C. 확정 사실 (나중에 착각하지 않도록)

- 오늘 `404`, `405`, `500`은 실제 오류로 확인한 것이 아니라 의미와 발생 조건을 학습한 것이다. 실제 실행에서 status code를 별도로 확인한 기록은 남기지 않았다.
- 현재 구현에서는 `GET /task`와 `POST /task` 모두 별도의 status code를 지정하지 않아 정상 응답은 기본 `200`이다. `201 Created`는 POST로 새 resource를 생성할 때 의미상 더 적절한 status code로 학습했지만 **실제 코드에는 적용하지 않았다.**

## D. 독립 / 교정 경계 (지점별)

**1. DOM element / collection / value**
- `querySelector()`가 element 하나를 반환한다는 판단은 처음에 틀려 **교정받았다.**
- `querySelectorAll()`로 얻은 collection을 `forEach()`로 순회할 때 parameter에 element 하나가 들어온다는 것은 후반 확인 문제에서는 **스스로 구분했다.**
- input element와 `.value`가 다르다는 개념은 설명 문제에서는 구분했지만, 실제 구현에서 입력창을 비울 때 `new_content.empty()`를 사용했고 `new_content = ""`이 가능한지도 질문했으므로 **실제 코드 적용에서는 교정이 필요했다.**

**2. browser ↔ Flask ↔ MongoDB 데이터 변환**
- `jsonify()`와 `response.json()`, `ObjectId → string → ObjectId` 흐름은 확인 문제에서 **스스로 설명했다.**
- `request.get_json()`을 통해 JSON request body가 Python에서 사용할 수 있는 데이터가 된다는 전체 흐름도 후반에는 **스스로 연결했다.**
- 반면 처음에는 `JSON.stringify()` 대신 `JSON.jsonify()`를 답했고, 실제 구현에서도 `Json.stringify()`라고 작성해 **교정받았다.**
- Flask가 `"tasks"`로 보낸 값을 JavaScript에서 `data.task_list`로 읽은 부분도 **교정받았다.**

**3. 상태 변경 버튼 / dataset / scope**
- 각 버튼에 `_id`를 연결하고 `querySelectorAll()`과 event callback을 사용해 PATCH 요청을 보내는 큰 구조는 **직접 작성했다.**
- 하지만 `important`를 버튼에 어떻게 보관할지에서 `updateButton.task.important`를 사용해 **교정받았고**, `data-important`와 `dataset`을 사용하는 방식도 **교정받았다.**
- `dataset`의 `"true"`가 string이라는 점을 실제 코드에서 바로 적용하지 못해 `=== true`를 사용했고 `"true"`와 비교하도록 **교정받았다.**
- `new_important`를 `if/else` block 내부에서 `let`으로 선언해 밖에서 사용할 수 없었던 것도 **교정받았다.**

**정리**
- 전체 CRUD 흐름을 전혀 모른 상태는 아니었지만, 세부 값의 위치·type·scope를 실제 코드에 연결하는 과정에서는 여러 차례 교정이 필요했다.
