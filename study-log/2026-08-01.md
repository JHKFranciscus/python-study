# 2026-08-01 공부일지

## 한 줄 요약
추상 클래스와 다형성으로 세 종류의 상품을 하나의 `ProductManager`에서 다루고, JSON에 저장한 뒤 원래 클래스의 객체로 복원하는 상품 관리 프로그램을 구현했다.

## 오늘 한 일

**추상 클래스와 다형성**
- `ABC`와 `@abstractmethod`를 사용하여 `Product` 추상 클래스를 구현했다.
- `PhysicalProduct`, `DownloadProduct`, `SubscriptionProduct`가 `get_product_info()`와 `to_dict()`를 각각 오버라이딩하도록 만들었다.
- 서로 다른 상품 객체를 하나의 `ProductManager`에서 등록·조회·검색·가격 변경·삭제하도록 구현했다.

**값 검증**
- `@property` setter로 가격의 자료형과 음수 여부를 검증했다.

**JSON 저장과 복원**
- 상품 종류와 클래스별 추가 속성을 JSON에 함께 저장했다.
- 저장된 `type` 값에 맞는 실제 클래스의 객체로 복원했다.
- JSON 딕셔너리를 상품 객체로 변환하는 `create_product_from_dict()`를 파일 읽기에서 분리했다.

**재현과 비교**
- 기존 코드를 보지 않고 추상 클래스·다형성·가격 검증·JSON 저장과 복원을 포함한 상품 관리 프로그램을 독립 재현했다.
- 객체 종류를 `isinstance()`로 외부에서 판별하는 방식과, 객체의 `to_dict()`를 호출하는 다형성 방식을 비교했다.

## 막힌 부분
1. 독립 재현 중 `to_dict()` 추상 메서드에 `self`를 빠뜨렸고, `DownloadProduct`의 출력 문자열을 일반 상품 형식으로 잘못 작성했다.
2. 가격 변경과 삭제 기능은 정상적으로 작동했지만, 테스트 코드에서 확인해야 할 결과 일부를 출력하지 않았다.
3. `create_product_from_dict()`를 `ProductManager`에 속한 메서드처럼 호출하여 `AttributeError`가 발생했다.
4. 일반 함수로 바꾼 뒤에도 함수가 정의되기 전에 호출하여 `NameError`가 발생했다.

## 시도한 것
- 구현 전에 클래스별 속성·메서드와 `ProductManager`의 역할을 주석으로 먼저 정리했다.
- (3번) 오류가 난 호출문을 확인하여 일반 함수와 인스턴스 메서드의 호출 방식을 구분했다.
- (4번) `create_product_from_dict()`를 상품 클래스 아래, `ProductManager` 위로 옮기고 함수 이름으로 직접 호출했다.
- (2번) 저장 전과 복원 후의 출력, 복원된 실제 클래스, 가격 변경 실패 후 기존 가격을 각각 확인했다.
- 동일한 상품을 `isinstance()` 방식과 다형성 방식으로 변환하여 결과가 같은지 비교했다.

## 배운 것

**다형성과 추상 클래스**
- 다형성에서는 같은 메서드를 호출해도 실행 시점의 실제 객체 클래스에 따라 오버라이딩된 메서드가 선택된다.
- 추상 클래스는 자식 클래스가 반드시 구현해야 할 공통 메서드를 강제할 수 있다.

**JSON 저장과 복원**
- JSON은 Python 객체의 클래스 정보를 보존하지 않으므로, 상품 종류를 나타내는 값을 별도로 저장해야 한다.
- JSON 복원 시 각 클래스의 생성자를 다시 호출하면 기존 property setter의 검증도 다시 적용된다.

**함수 구조**
- 클래스 밖에 정의한 일반 함수는 객체나 클래스 이름을 거치지 않고 함수 이름으로 직접 호출한다.
- 파일 읽기와 객체 생성을 분리하면 각 함수가 담당하는 역할이 더 명확해진다.

**`isinstance()`와 다형성 비교**
- `isinstance()` 방식은 새로운 상품 종류가 추가될 때 외부 조건문도 함께 수정해야 한다.
- 다형성 방식은 새 클래스가 공통 메서드를 구현하면 기존 반복문과 변환 함수를 그대로 사용할 수 있다.

## 아직 모르는 것
- 상품 종류가 늘어날 때 `create_product_from_dict()`의 `if`·`elif`도 수정하지 않는 구조를 만드는 방법은 아직 모른다.
- 추상 클래스와 일반 부모 클래스를 선택하는 구체적인 기준이 아직 익숙하지 않다.
- `isinstance()`가 필요한 경우와 다형성으로 대체해야 하는 경우를 아직 정확히 구분하지 못한다.

## 내일 할 일
- 4주차에 학습한 클래스·상속·오버라이딩·캡슐화·property·추상 클래스·다형성을 전체 복습한다.
- 객체지향 상품 관리 프로그램의 핵심 구조를 보지 않고 다시 재현한다.
- 4주차 주간 기록과 공개 글 초안을 작성한다.

## 면접 대비 정리 (선택)

**Q. 오늘 만든 프로그램을 설명해 주세요.**
`Product` 추상 클래스를 만들고 `PhysicalProduct`, `DownloadProduct`, `SubscriptionProduct`가 `get_product_info()`와 `to_dict()`를 각각 오버라이딩하게 해서, 서로 다른 상품을 하나의 `ProductManager`에서 등록·조회·검색·가격 변경·삭제할 수 있게 만들었습니다. 가격은 `@property` setter에서 자료형과 음수 여부를 검증했고, 상품 종류를 JSON에 함께 저장해 `type` 값에 맞는 실제 클래스의 객체로 복원했습니다.

**Q. 오류를 어떻게 해결했나요?**
`create_product_from_dict()`를 `ProductManager`의 메서드처럼 호출해서 `AttributeError`가 났습니다. 호출문을 확인해 일반 함수와 인스턴스 메서드의 호출 방식이 다르다는 걸 구분했고, 일반 함수로 바꾼 뒤에는 정의 전에 호출해서 `NameError`가 났습니다. 함수를 상품 클래스 아래, `ProductManager` 위로 옮기고 함수 이름으로 직접 호출해서 해결했습니다.

**Q. 가장 크게 배운 점은 무엇인가요?**
같은 기능을 `isinstance()` 방식과 다형성 방식으로 각각 구현해 결과가 같은지 비교해 봤습니다. `isinstance()` 방식은 새 상품 종류가 늘어나면 외부 조건문까지 고쳐야 하지만, 다형성 방식은 새 클래스가 공통 메서드만 구현하면 기존 반복문과 변환 함수를 그대로 쓸 수 있다는 차이를 확인했습니다.
