# 2026-09-18 — EC2에 Nginx reverse proxy 추가

**한 줄 요약**
Gunicorn을 :5000으로 외부에 직접 노출하던 구조를, Nginx가 :80에서 모든 request를 받고 Gunicorn은 내부에서만 받는 구조로 바꿨다.

**키워드 앵커**
`reverse proxy` `proxy_pass` `nginx -t` `0.0.0.0 → 127.0.0.1` `Security Group 5000 삭제` `장애 위치 좁히기`

---

## 1. 무엇이 어떻게 바뀌었나

어제까지:

```
Browser → Public IPv4:5000 → Gunicorn → Flask → MongoDB
```

오늘부터:

```
Browser → Public IPv4:80 → Nginx → 127.0.0.1:5000 → Gunicorn → Flask → MongoDB
```

웹 애플리케이션의 외부 진입점은 Nginx의 :80 하나로 정리됐다.

---

## 2. Nginx를 Gunicorn 앞에 붙이기

- Nginx 설치 후 `systemctl`, `ss`로 확인했다. 이 시점에는 Nginx(:80)와 Gunicorn(:5000)이 서로 모르는 상태로 각각 돌고 있었다.
- 증거: `curl http://127.0.0.1/` 결과가 Flask가 아니라 **Nginx 기본 페이지**였다.
- `location /`에 `proxy_pass http://127.0.0.1:5000;`을 넣어 두 process를 이어 붙였다.
- 수정 후 바로 reload하지 않고 `sudo nginx -t`로 문법을 먼저 검사한 뒤 reload했다.
- 결과: 같은 `curl http://127.0.0.1/`이 이번엔 **Flask 페이지**를 반환했다. Windows browser에서 `http://PublicIPv4`로 들어가도 Flask 페이지와 기존 MongoDB data가 정상 조회됐다.

> 같은 명령의 응답이 바뀐 것 자체가 연결이 생겼다는 증거다.

---

## 3. Gunicorn을 내부 전용으로 내리기

- 이제 외부 request는 Nginx가 받으므로, Gunicorn이 바깥을 향해 열려 있을 이유가 없어졌다.
- bind를 `0.0.0.0:5000` → `127.0.0.1:5000`으로 변경했다.
- 변경 후 `ss` 결과: Nginx `0.0.0.0:80`, Gunicorn `127.0.0.1:5000`.
- AWS Security Group에 남아 있던 5000 inbound rule도 삭제했다.

---

## 4. reboot 후 자동 복구 검증

EC2를 reboot한 뒤 확인한 것:

- kernel `6.17.0-1017-aws`
- `mongod` / `flask-study` / `nginx` 모두 active
- port도 `0.0.0.0:80`(Nginx), `127.0.0.1:5000`(Gunicorn)으로 복구
- 내부 `curl http://127.0.0.1/` → Flask HTML 정상, Windows browser에서도 Flask 페이지 + MongoDB data 정상

→ 손으로 다시 올리지 않아도 `Nginx → Gunicorn → Flask → MongoDB`가 자동으로 다시 동작한다.

---

## 5. 오늘 이해한 핵심 4가지

1. **Nginx와 Gunicorn은 역할이 다르다.** Nginx는 외부 HTTP request를 먼저 받고, Gunicorn은 Flask application을 실행해 request를 Flask에 전달한다. 대체 관계가 아니라 앞뒤로 연결해서 쓴다.
2. **같은 server 안에서도 port에 따라 연결되는 process가 다르다.** :80은 Nginx, :5000은 Gunicorn. IP만으로 정해지지 않는다.
3. **`0.0.0.0`과 `127.0.0.1`은 다르다.** `0.0.0.0`은 여러 network interface에서 받을 수 있고, `127.0.0.1`은 같은 computer 내부에서 오는 request만 받는다. 그래서 지금 Gunicorn은 EC2 내부에서만 접근된다.
4. **Flask가 EC2에서 돌고 있다고 browser가 알아서 찾아오는 게 아니다.** 중간 process나 port 연결이 끊기면 다른 경로를 자동으로 찾지 않는다.

---

## 6. 장애 위치 좁히는 법 (오늘 제일 남는 것)

문제가 생기면 명령부터 치지 말고, **어디까지 정상인지**를 먼저 확인해 범위를 좁힌다.

기본 순서: `service 상태 → log → port LISTEN → EC2 내부 HTTP → 외부 network / Security Group`

성공한 지점이 곧 다음 의심 범위를 정해준다.

- :5000 직접 접속 성공 → Gunicorn + Flask까지는 정상
- :80 내부 접속 성공 → Nginx → Gunicorn → Flask까지 정상
- 내부 :80은 성공인데 외부 browser만 실패 → Public IPv4 / Security Group 등 외부 network 쪽 의심

---

## 7. 오늘의 교정 (착각 → 확인한 사실)

1. Nginx 설정 파일에서 `#`으로 comment 처리된 예제 부분을 수정하려 했다.
   → `#`이 붙은 줄은 실제 설정으로 실행되지 않는다. 실제 `try_files`가 들어 있는 `location /` block을 찾아 수정했다.
2. "Flask가 AWS에서 실행 중이면 browser에서 직접 접근할 수 있다"고 생각했다.
   → 접속 경로는 **어떤 IP:port에서 어떤 process가 LISTEN하고 있는지**에 따라 결정된다.

---

## 8. 현재 수준 (솔직하게)

오늘 실제 EC2에서 해본 것: Nginx 설치 / reverse proxy 구성 / Gunicorn 내부 bind 전환 / Security Group 5000 제거 / reboot 후 자동 복구 검증 / Nginx 포함 장애 위치 추적.

다만 Nginx 설정과 장애 진단을 **아무것도 보지 않고 혼자 구성할 수준은 아직 아니다.** 지금은 구조와 각 process의 역할을 이해하고, 안내를 참고해 실제 서버에서 구성·검증한 단계다.

## 예상 꼬리질문과 답변 방향

- **Nginx를 왜 굳이 앞에 두나요?**
  → 오늘 확인한 범위에서 솔직하게: 외부 진입점을 하나로 모으고 Gunicorn을 내부 전용으로 내릴 수 있었다. 그 외 일반적인 장점은 아직 직접 체감해본 게 아니라고 말하는 편이 안전하다.
- **0.0.0.0과 127.0.0.1의 차이는요?**
  → 0.0.0.0은 여러 network interface에서 request를 받고, 127.0.0.1은 같은 machine 내부 request만 받는다. Gunicorn을 127.0.0.1:5000에 bind해 외부 interface에서 직접 받지 않도록 했고, Security Group의 5000 inbound rule도 삭제했다.
- **`nginx -t`는 왜 했나요?**
  → 설정 문법이 틀린 채로 reload하면 문제가 되니, 적용 전에 문법을 먼저 검사했다.
- **문제가 생기면 어떻게 찾아가나요?**
  → 6번 섹션의 순서(service → log → port → 내부 HTTP → 외부 network)를 그대로 말하면 된다. 성공한 지점을 기준으로 의심 범위를 좁힌다고 설명.
- **혼자 다 하신 건가요?**
  → 구조와 각 process 역할은 이해했지만 설정을 아무것도 안 보고 짤 수준은 아니라고 솔직히 말하는 게 낫다.
