## 1. 오늘의 결과

오늘은 CRUD 기능을 하나씩 연습하는 데서 끝나지 않고, 지금까지 배운 기능을 **하나의 실제 프로그램 흐름으로 연결했다.**

최종적으로 다음을 한 프로그램에서 동작시켰다.

* 공부 기록 등록 / 전체 조회 / 수정 / 삭제
* subject filter
* 시작 날짜 / 종료 날짜 / 날짜 범위 조회
* 최신순 / 오래된순 정렬
* 여러 조건을 함께 사용하는 복합 조회
* 공용 수정 form을 이용한 record 수정
* 수정 취소
* PATCH / DELETE 후 현재 filter 상태 유지
* 빈 memo `""` 수정
* server error → JavaScript `catch` 연결

**최종 browser 요구 테스트는 전부 통과했다.**

다만 오늘 결과를 **완전 독립 성공**으로 평가하지는 않는다.

* CRUD와 client의 **큰 구조는 직접 구성했다.**
* 공용 수정 form + `editingId`라는 새로운 구조도 직접 만들었다.
* 하지만 server와 client의 여러 세부 오류는 피드백을 받아 수정했고, server의 주요 수정 코드는 그대로 적용했다.

따라서 현재 상태는:

> **큰 구조와 data flow는 직접 구성할 수 있지만, 코드가 길어질 때 API 계약·optional 값·HTTP method·Promise·state 초기화 같은 세부 일관성 오류가 아직 발생한다.**

## 2. 오늘 한 일

* Flask + MongoDB CRUD, filter, 날짜 범위 조회, sort, PATCH, DELETE를 하나의 공부 기록 관리 프로그램으로 통합했다.
* POST / GET / PATCH / DELETE의 URL, HTTP method, request body, query parameter를 먼저 정리했다.
* GET에서 `subject`, `start_date`, `end_date`, `sort`를 조합해 복합 조회를 구현했다.
* client에서는 전날의 record별 수정 input 대신 **공용 수정 form 하나 + `editingId`** 구조를 만들었다.
* 수정 button을 누르면 해당 `_id`를 `editingId`에 저장하고 기존 값을 공용 form에 표시했다.
* 저장할 때는 `editingId`로 수정 대상을, form value로 새 값을 결정했다.
* PATCH / DELETE 후 `loadRecords()`를 호출해 현재 filter 상태를 유지하면서 최신 DB data로 다시 render했다.
* CS에서는 `fetch()` → Flask → MongoDB → HTTP response → JavaScript의 전체 왕복 흐름을 연결했다.
* SSAFY는 개인 사정으로 생략했다.

## 3. 오늘의 핵심 — state의 위치를 구분하기

현재 프로그램의 state는 한곳에 있지 않다.

* 실제 저장된 공부 기록 → **MongoDB**
* 현재 filter와 수정 form의 값 → **DOM**
* 현재 수정 대상 → **`editingId`**
* 현재 화면 목록 → **마지막 GET 결과를 기반으로 만든 render 결과**

특히:

* `editingId` → **어느 document를 수정할지**
* form value → **어떤 값으로 수정할지**

를 결정한다.

또한 PATCH가 성공해 MongoDB가 바뀌어도 기존 DOM이 자동으로 바뀌는 것은 아니다.

```text
PATCH 성공
→ MongoDB 변경
→ GET 재조회
→ 최신 DB data
→ 다시 render
```

과정을 거쳐야 화면도 최신 상태가 된다.

## 4. 막힌 점과 교정

### Server

* POST subject validation이 빈 string을 통과시킬 수 있었음
* 계약은 `/record/<record_id>`였지만 PATCH route를 `/records/<record_id>`로 작성함
* optional `subject`의 존재 여부를 확인하기 전에 값을 읽음
* PATCH update data에서 `subject` 조건을 반복 작성함
* DELETE route에서 `methods=["DELETE"]`를 빠뜨림

### Client

* 수정 취소 동작 누락
* PATCH 성공 후 `editingId = null` 누락
* POST / DELETE error 처리에서 Promise `return` 누락
* memo를 `""`으로 수정하는 경우 누락

피드백 후 모두 수정했고 전체 browser 테스트를 통과했다.

특히 다시 확인한 것은:

```text
field가 없음
≠
field가 존재하지만 value가 ""
```

이라는 차이다.

## 핵심 꼬리질문

### Q1. 직접 한 것과 도움받은 것은?

큰 CRUD 구조, 복합 조회, 공용 form + `editingId`, filter 상태 유지 재조회는 직접 구성했다. server와 client의 세부 오류는 피드백을 받아 수정했다.

### Q2. `editingId`는 왜 필요한가?

여러 record가 공용 수정 form 하나를 사용하므로 현재 어느 document를 수정 중인지 별도로 기억하기 위해 사용했다.

### Q3. PATCH 후 왜 GET을 다시 하는가?

DB가 바뀌어도 기존 DOM은 자동으로 바뀌지 않는다. 최신 DB data를 다시 받아 화면을 맞추고, 기존 filter 상태도 그대로 유지하기 위해 다시 조회했다.

### Q4. 가장 기억나는 오류는?

계약은 `/record/<record_id>`였는데 실제 PATCH route를 `/records/<record_id>`로 작성했다. 이 오류를 통해 각 코드의 문법뿐 아니라 client와 server가 같은 API 계약을 사용하는지도 확인해야 한다는 점을 배웠다.
