# 공부일지 — Flask + MongoDB 날짜 범위 조회 / 정렬 / 상태 유지 재조회

한 줄 요약: 값이 있는 filter만 골라 하나의 MongoDB query로 조립하고, PATCH / DELETE 후에도 같은 조회 function을 다시 불러 filter 상태를 유지했다.

## 오늘 한 일

* Flask + MongoDB GET 조회에 날짜 범위 조건을 추가했다. `$gte`, `$lte`로 시작일만 있는 경우 / 종료일만 있는 경우 / 둘 다 있는 경우를 처리했다.
* category exact-match filter와 날짜 범위 filter를 하나의 query에 결합하고, `sort()`로 최신순 / 오래된순 정렬을 붙였다.
* client에서는 `URLSearchParams`로 값이 있는 filter만 optional query parameter로 만들었고, filter의 `change` event가 발생하면 조회 function을 다시 실행했다.
* 독서 기록 관리 페이지에서 등록 / 조회 / 수정 / 삭제에 category / 날짜 범위 / 정렬을 연결하고, PATCH / DELETE 후에도 현재 filter 상태를 유지한 채 다시 조회하도록 했다.
* invalid category, invalid sort, 시작일이 종료일보다 뒤인 경우에 HTTP 400을 반환했고, client는 `response.ok → error response body parsing → throw → catch` 흐름으로 받았다.
* 실제 브라우저에서 전체 / category 단독 / 시작일 단독 / 종료일 단독 / 날짜 범위 / category + 날짜 범위 / 최신순 / 오래된순 / PATCH 후 상태 유지 / DELETE 후 상태 유지 / 400 세 가지를 모두 확인했다.

## 막힌 부분

독립 재현에서 큰 구조와 주요 데이터 흐름은 직접 구성했지만, 구현 도중 다음 오류들을 Claude의 도움을 받아 수정했다.

* category select에 전체 조회용 빈 value가 없어서 category filter가 항상 붙었다.
* POST에서 HTTP error를 Promise error 흐름으로 넘기는 처리가 빠져 있었다.
* `.catch()`에서 error를 받고도 실제로 출력하거나 처리하지 않았다.
* `queryString`, `url`, `new_pages`를 선언 없이 사용했다.
* `params.append("start_date", startDate)`의 `"start_date"`를 query parameter name이 아니라 object의 property처럼 판단했다.
* Flask에서 `_id`를 이미 `str()`로 바꿔 놓고, JavaScript 쪽 최종 데이터를 적을 때 다시 `ObjectId(...)`라고 적었다.

앞의 네 개는 써야 할 코드를 빠뜨린 것이고, 뒤의 두 개는 이름과 type을 잘못 읽은 것이다.

## 시도한 것

날짜 filter는 `start_date`, `end_date`를 document의 별도 field로 넣지 않고, 실제 날짜 field 하나에 range operator를 조립했다.

```python
date_query = {}

if start_date:
    date_query["$gte"] = start_date

if end_date:
    date_query["$lte"] = end_date

if date_query:
    query["read_date"] = date_query
```

filter가 바뀔 때 변경된 값만 argument로 넘기지 않고, 조회 function이 실행될 때 현재 DOM의 모든 filter `.value`를 다시 읽게 했다. 그래서 PATCH / DELETE 성공 후 같은 `loadBooks()`를 다시 호출하는 것만으로 filter와 정렬 상태가 유지됐다.

## 배운 것

**1. exact-match와 range는 query 내부 구조가 다르다**

```python
"category": "programming"                                   # value가 string
"read_date": {"$gte": "2026-09-04", "$lte": "2026-09-10"}   # value가 operator를 가진 dictionary
```

`find(query)`는 어떤 document가 결과에 포함되는지를 정하고, `sort()`는 그렇게 선택된 결과의 순서를 정한다.

**2. 비슷하게 생긴 이름은 자동으로 이어지지 않는다**

```text
HTML id            start-date
JavaScript 변수    startDate
query parameter    start_date
Flask 변수         start_date
MongoDB field      read_date
MongoDB operator   $gte
```

`URLSearchParams.append()`의 첫 번째 argument는 query parameter의 name이고 두 번째가 value다. 이 이름들은 내가 직접 이어줘야 연결된다.

**3. 하나의 filter만 바꿔도 나머지가 유지되는 이유**

`change` event로 조회 function이 실행될 때, 그 시점의 모든 filter DOM 값을 다시 읽기 때문이다.

**4. `YYYY-MM-DD` 문자열을 날짜 비교에 쓸 수 있는 이유와 한계**

큰 단위부터 작은 단위까지 자릿수가 고정돼 있어 문자열 비교 순서와 날짜 순서가 일치한다. 다만 날짜만 저장하므로 시각과 timezone이 필요한 요구사항에는 충분하지 않다.

## 아직 부족한 부분

오늘 독립 재현은 완전 독립 성공이 아니다. 정확한 평가는 **요구사항을 보고 Flask / HTML / JavaScript의 큰 통합 구조와 날짜 범위 조회, 정렬, 상태 유지 재조회 흐름을 직접 구성 → 세부 오류 발생 → Claude의 도움으로 일부 수정 → 추가 교정 → 브라우저에서 요구 기능 전체 동작 확인**이다. 구조를 구성하지 못했다고 볼 것도, 도움 없이 끝냈다고 볼 것도 아니다.

연결 판단에서 실제 value를 구체적으로 쓰지 않거나, 중간에 변환한 type을 최종 단계까지 유지하지 못한 경우가 있었다. 긴 흐름을 볼 때는 계속 이 순서로 확인한다.

```text
현재 변수의 실제 value → type → collection / element 여부
→ 다음 단계에서 사용되는 이름 → argument / parameter 전달
→ 중간 type 변환 → 최종 단계의 value와 type
```

## 내일

오늘의 오류를 이유로 보충일을 만들거나 본 진도를 줄이지 않는다. optional filter, 날짜 범위 query, 정렬을 처음부터 다시 반복하지 않고 현재 4단계의 다음 본 진도로 진행한다. 이후 진도 안에서 필요할 때 실제 value, type, collection / element, argument / parameter 연결을 짧게 확인한다.
