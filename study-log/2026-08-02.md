## 막힌 부분

**개념**

객체지향 용어를 코드 없이 설명할 때 클래스·객체·인스턴스의 의미가 정확히 구분되지 않았다. 추상 클래스의 목적도 처음에는 공통 메서드를 모으는 것으로만 설명했고, `isinstance()`를 사용해도 되는 상황을 구분하지 못했다.

**독립 재현**

JSON 저장 후 새로운 관리자 객체에서 상품이 처음에는 복원되지 않았다. 또한 파일이 없거나 JSON 형식이 잘못되었을 때 기존 상품 목록이 그대로 남았고, 가격 변경 실패 원인도 모두 `False`로 처리하여 구분되지 않았다.

## 시도한 것

**개념**

각 개념을 정의만 적지 않고 짧은 코드의 실행 결과와 연결해 다시 설명했다. 클래스 속성과 같은 이름을 인스턴스에 대입한 결과, 생성자에서 프로퍼티 setter가 호출되는 과정, 추상 클래스의 객체 생성 실패를 직접 실행해 확인했다.

**독립 재현**

`create_product()`, `save()`, `load()`의 실행 흐름을 확인했다. 없는 파일과 잘못된 JSON 파일을 따로 만들어 예외 상황을 테스트했고, 가격 변경 뒤 반환값과 실제 객체의 가격도 출력해 확인했다.

## 배운 점

- **인스턴스의 정의** — 인스턴스는 클래스와 객체를 연결하는 요소가 아니라, 특정 클래스로부터 실제로 생성된 객체이다.
- **클래스 속성 가리기** — 인스턴스에서 클래스 속성과 같은 이름에 값을 대입하면 클래스 속성이 바뀌는 것이 아니라, 같은 이름의 인스턴스 속성이 생성되어 클래스 속성을 가릴 수 있다.
- **생성 시점의 값 검사** — 프로퍼티 setter를 생성 시점에도 적용하려면 생성자에서 내부 속성인 `self._price`에 직접 저장하지 않고 `self.price`를 사용해야 한다.
- **추상 클래스의 목적** — 단순히 공통 메서드를 모으는 용도가 아니라, 자식 클래스가 반드시 구현해야 하는 동작의 형식과 규칙을 강제한다.
- **반환과 상태 변경의 차이** — `return`이나 `return []`은 함수의 실행이나 반환값에만 영향을 주며, `self.products` 같은 객체의 상태를 자동으로 변경하지 않는다.
- **실패 원인의 구분** — 상품이 존재하지 않는 경우와 가격이 잘못된 경우처럼 실패 원인이 다르면, 반환값과 예외도 구분해야 한다.

## 아직 모르는 점

- 객체지향 개념을 코드 없이 정확한 문장으로 설명하는 것은 아직 불안정하다.
- 상속과 객체 구성은 단순한 관계에서는 구분할 수 있지만, 여러 객체가 연결된 새로운 문제에서는 어느 구조가 적절한지 바로 판단하기 어렵다.
- 정상 동작뿐 아니라 예외가 발생했을 때 기존 객체 상태를 유지할지 초기화할지를 설계 단계에서 결정하는 연습이 더 필요하다.
