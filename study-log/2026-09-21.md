# 공부일지 · 2026-09-21

> **한 줄 요약** 기존 EC2에서 두 번째 재배포를 직접 수행하고, reboot 이후까지 검증해 5단계 AWS 배포를 종료했다.
>
> **키워드** file 최신 ≠ process 최신 · 검증 순서 = 장애 위치 판단 순서 · restart vs reboot

## 1. 오늘 한 일

- 기존 EC2 상태를 직접 확인했다: Git repository 상태 / `mongod` / `flask-study` / `nginx` / LISTEN 중인 address·port
- local에서 Flask application의 title을 수정하고, 재배포 흐름을 직접 구성해 수행했다.

```
local 수정 → git add / commit / push
→ EC2 git pull → systemctl restart flask-study
→ curl :5000 → curl :80 → Windows browser
```

- `sudo reboot` 후 다시 접속해 `mongod` / `flask-study` / `nginx`가 모두 active / enabled인 것을 확인했다.

**결과**

- 새 version인 `redeploy2`가 내부·외부 모두 적용됐다.
- reboot 후에도 `127.0.0.1:5000` / `127.0.0.1:80` / Windows browser에서 새 version이 정상 동작했다.

## 2. file 최신 ≠ process 최신

- file / program: disk에 저장된 code
- process: 실제 실행 중인 program

```
git pull → disk의 code file만 최신화
systemctl restart flask-study → 기존 process 종료 → 최신 code를 읽는 새 process 실행
```

→ `git pull`만으로는 이미 실행 중인 Gunicorn process가 새 code로 바뀌지 않는다.

## 3. 검증 순서 = 장애 위치 판단 순서

```
Windows browser
→ 외부 network / Public IPv4 / Security Group
→ Nginx     :80 LISTEN
→ Gunicorn  127.0.0.1:5000 LISTEN  (Flask)
→ MongoDB   127.0.0.1:27017 LISTEN (DB가 필요한 작업일 때)
```

확인은 안쪽(`:5000`)부터 바깥으로 한다.

- `curl :5000` 실패 → flask-study / Gunicorn / Flask 쪽
- `:5000` 성공 + `:80` 실패 → Nginx 쪽
- EC2 내부 `:80` 성공 + Windows browser 실패 → Public IPv4 / Security Group / 외부 network 쪽
- MongoDB만 죽은 경우 → `:5000` connection은 될 수 있다. 하지만 DB가 필요한 작업은 `Flask → 127.0.0.1:27017 → MongoDB` 구간에서 실패할 수 있다.

**용어**

- socket: process가 network 통신에 쓰는 통신 지점
- LISTEN: connection을 기다리는 상태
- endpoint: address + port

## 4. 교정

1. `git status`의 `Your branch is up to date with 'origin/main'.`만으로 지금 GitHub server의 최신 commit까지 확인했다고 단정할 수 없다.
   → `origin/main`은 local repository가 마지막으로 알고 있는 remote-tracking reference이기 때문이다.
2. Flask code만 반영할 때는 `sudo systemctl restart flask-study`를 쓴다.
   → `sudo reboot`도 결과적으로 process를 다시 실행시키지만 EC2 전체를 재부팅한다. 오늘 reboot는 code 반영이 아니라 boot 이후 service 자동 재실행 검증용이었다.

## 5. 5단계 종료 → 6단계

- AWS/Linux 운영을 완전히 숙련한 건 아니다.
- 하지만 5단계에서 요구한 범위는 실제로 수행하고 검증했다.
  - EC2 배포 / Gunicorn + systemd / Nginx reverse proxy / Git 기반 재배포
  - 내부·외부 검증 / reboot 후 자동 실행 검증 / 기본 장애 위치 판단 / 두 번째 재배포 독립 수행
- 다음 학습일부터 **6단계 — 정글 입학시험 형태 연습 + SSAFY 완성**
- 오늘 SSAFY는 내가 생략하기로 했다. 실패·미완료·이월로 치지 않는다.

## 면접 부록

**30초 스크립트**

> EC2에 Flask 앱을 Gunicorn, systemd, Nginx로 배포했고, 두 번째 재배포는 흐름을 직접 구성해서 수행했습니다. local에서 수정해 push하고, EC2에서 pull한 뒤 service를 restart했습니다. git pull은 파일만 최신으로 바꾸고 이미 실행 중인 process는 그대로라서, restart를 해야 새 code가 반영됩니다. 검증은 5000번, 80번, 외부 브라우저 순서로 했고, reboot 후에도 세 service가 자동으로 다시 실행되는지까지 확인했습니다.

**예상 꼬리질문 → 답변 방향**

- 왜 `git pull`만으로 반영이 안 되나요? → file과 process는 다르다. restart로 새 process를 띄워야 최신 code를 읽는다.
- 접속이 안 되면 어디부터 보나요? → `:5000` → `:80` → 외부 순서로 좁힌다. 실제 장애 사례가 없으면 "판단 기준을 정리한 수준"이라고 솔직하게 말한다.
- reboot는 왜 했나요? → code 반영은 restart로 한다. reboot는 boot 이후 service가 자동으로 다시 실행되는지 검증하려고 했다.

**빈틈 체크**

- [ ] 실제로 장애를 겪고 위치를 찾은 사례가 있는지 (이전 일지 확인)
- [ ] `enabled`와 boot 이후 자동 실행이 어떻게 연결되는지 (일지에 없음)
- [ ] GitHub server의 최신 commit을 실제로 확인하는 방법 (일지에 없음)
