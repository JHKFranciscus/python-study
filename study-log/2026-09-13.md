## 막힌 부분

독립 재현의 첫 구현에서 다음 오류가 있었다.

- latest / oldest인데 `priority`를 기준으로 sort함
- 현재 status에 따른 다음 상태만 제공해야 했지만 모든 status 변경 button을 만듦
- invalid priority response body는 만들었지만 HTTP 실패 status를 지정하지 않음

복습에서는 다음 세부 구분에서 실수가 있었다.

- 현재 filter state와 `editingId`의 위치
- `request.args.get()`에는 query parameter의 value가 아니라 key를 넣는다는 점
- HTTP status와 parsing된 response body의 역할 구분

## 시도한 것

독립 재현에서는 기존 프로그램의 수정 구조를 그대로 가져오지 않고, 현재 요구사항에서 PATCH할 순간 필요한 값이 어디에 있는지 다시 판단했다.

이번 구조에서는 button의 event callback에서:

- `task._id` → 수정할 document
- `task.status` → 다음 status를 판단하기 위한 현재 값

을 바로 얻을 수 있었기 때문에 별도의 `editingId`가 필요하지 않았다.

피드백 후에는 sort 기준, status 전이 UI, validation의 HTTP status를 수정하고 browser에서 다시 테스트했다.

추가로 Console에서 다음도 확인했다.

- invalid priority → `400 Bad Request`
- invalid status → `400 Bad Request`
- 형식은 유효하지만 존재하지 않는 document의 PATCH → `404 Not Found`
- 형식은 유효하지만 존재하지 않는 document의 DELETE → `404 Not Found`

## 배운 점

`editingId` 같은 state는 수정 기능이 있다고 무조건 필요한 것이 아니다.

수정 대상을 선택하는 시점과 실제 request를 보내는 시점이 떨어져 있다면 수정 대상을 기억할 state가 필요하지만, request 시점에 `_id`를 바로 얻을 수 있다면 별도로 저장할 필요가 없다.

또 다음 두 가지를 다시 확인했다.

```text
코드가 실행됨
≠
요구사항대로 동작함
```

이번에는 `.sort("priority", ...)`가 정상 실행됐지만 latest / oldest라는 요구사항과 실제 정렬 기준이 달랐다.

그리고:

```text
HTTP 400 / 404 response 수신
→ fetch() 자체는 기본적으로 fulfilled

server 연결 자체 실패
→ fetch() rejected
```

이므로 HTTP 실패 status를 `.catch()`로 보내려면 `response.ok`를 확인한 뒤 직접 `throw`해야 한다.

## 아직 모르는 점 / 부족한 점

현재 Flask + MongoDB CRUD의 큰 구조를 시작하지 못하는 상태는 아니다.

구조가 다른 작업 관리 프로그램에서도 큰 흐름을 직접 구성했다.

다만 코드가 길어졌을 때 다음 세부 일관성은 아직 안정적이지 않다.

- API 계약과 실제 구현 일치
- optional field 존재 여부
- 빈 값과 field 부재 구분
- HTTP status와 response body 구분
- 어떤 state를 유지하고 어떤 state만 초기화할지 판단
- sort / filter의 실제 기준이 요구사항과 같은지 확인

오늘 독립 재현은 **부분 독립 성공**으로 평가한다.

큰 CRUD와 새로운 PATCH data flow는 직접 구성했지만, sort 기준·status UI·HTTP status 오류는 피드백 후 수정했기 때문에 완전 독립 성공으로 기록하지 않는다.
