# 2026-09-04 · 9주차 5일차 공부일지

**한 줄 요약**
JavaScript `fetch()` → Flask → MongoDB → JSON response → DOM 갱신까지 Ajax CRUD 전체 흐름을 직접 연결하고, status code로 실패 지점을 좁혀 디버깅했다.

**키워드**: fetch, Ajax CRUD, JSON.stringify, jsonify, ObjectId, status code(404 / 400 / 415 / 200), callback

---

## 1. 오늘 한 것

- `fetch()`로 Flask API에 GET / POST / PATCH / DELETE request를 보내고, MongoDB CRUD 결과를 JSON response로 받아 DOM에 반영했다.
- 데이터가 오가는 **방향**을 기준으로 네 가지를 구분했다.
  - JS → 서버: `JSON.stringify()` (보낼 때) / `request.get_json()` (받을 때)
  - 서버 → JS: `jsonify()` (보낼 때) / `response.json()` (받을 때)
- MongoDB `ObjectId`는 JS로 보낼 때 string으로 바꾸고, 수정·삭제 요청이 오면 Flask에서 다시 `ObjectId`로 되돌렸다.
- CRUD 성공 후 `loadMovies()` / `loadTasks()`를 다시 실행해, 페이지 전체 새로고침 없이 최신 DB 상태로 화면을 갱신했다.
- **영화 CRUD를 학습한 뒤, 할 일 관리 웹을 독립 재현**해 조회 · 등록 · 완료 상태 변경 · 삭제를 구현했다.
- CS: HTML response와 JSON response의 body와 `Content-Type` 차이, `jsonify()`와 `response.json()`의 차이를 정리했다.

## 2. 막힌 것 → 원인 → 배운 것

**A. request가 Flask에 제대로 도착하지 않은 경우**

1. `GET /app.js 404` — static JavaScript 경로 오류 → **404는 요청한 파일/route를 못 찾은 것**이다.
2. `400` — POST body에 `JSON.stringify()`를 빠뜨림 → **400은 body가 서버가 기대한 형태가 아닌 것**이다.
3. `415` — PATCH의 `Content-Type` 오타 → **415는 body 형식 자체를 서버가 받아주지 않은 것**이다.

**B. 화면에 잘못 그린 경우**

4. `[object Object]` 출력 — object 전체를 그대로 출력함 → 화면에 그릴 값은 **object에서 property를 꺼내** 써야 한다.
5. DOM element를 가리키던 변수에 빈 문자열을 다시 대입함 → element reference를 유지하고, 비울 때는 element의 innerHTML을 ''로 바꿔야 한다.

**C. 개념을 혼동한 경우 (독립 재현에서)**

6. `tasks` collection과 `task` element를 혼동 → 이름이 비슷해도 하나는 **DB 데이터**, 하나는 **화면 요소**다.
7. `querySelectorAll()` 결과를 하나의 element처럼 다룸 → 여러 개가 담긴 목록이므로 **반복해서** 접근해야 한다.
8. `addEventListener()`에 `updateTask(...)` / `deleteTask(...)`를 바로 호출해 넘김 → event listener에는 **실행 결과가 아니라 나중에 실행할 function 자체**를 넘겨야 한다.
9. `update_one()`에서 `$set` 누락 → MongoDB 수정은 **어떤 연산인지(`$set`) 명시**해야 한다.

## 3. 어떻게 확인했는지 (디버깅 방법)

- Flask terminal의 status code 흐름(`404 → 400 → 415 → 200`)을 보고 request가 **어느 단계에서** 실패했는지 좁혔다.
- API URL을 브라우저에서 직접 열어 Flask가 실제로 반환하는 JSON을 눈으로 확인했다.
- `mongosh`의 `find()`로 등록 · 수정 · 삭제가 MongoDB에 실제 반영됐는지 확인했다.
- POST / PATCH / DELETE 성공 뒤 GET request가 다시 발생하는 것을 확인해, `loadMovies()` / `loadTasks()`의 화면 갱신 흐름을 검증했다.

---

## 4. 오늘의 핵심 흐름

```
사용자 동작 → JavaScript → HTTP request → Flask route → MongoDB 작업
→ HTTP response → JavaScript → 최신 데이터 재조회 → DOM 갱신
```

- **DB가 바뀌었다고 화면이 자동으로 바뀌지 않는다.** JavaScript가 최신 데이터를 다시 받아 DOM을 갱신해야 한다.
- `forEach()`의 callback과 `addEventListener()`의 callback은 **실행 시점이 다른 function**이다. 앞은 지금 반복 실행되고, 뒤는 event가 발생한 뒤에 실행된다.

---

## 5. 아직 부족한 것

- collection과 element를 코드 중간에서 바로 구분하는 판단이 아직 안정적이지 않다.
- callback이 중첩되면 지금 실행되는 function과 event 후 실행되는 function이 헷갈린다.
- Ajax CRUD 전체 구조는 직접 구성했지만, 독립 재현에서 `JSON.stringify()`, `$set`, event listener 연결 같은 세부를 일부 빠뜨렸다.

## 부록 B. 예상 꼬리질문

- **"`jsonify()`와 `response.json()`은 어떻게 다른가요?"**
  → 하나는 Flask가 JSON response를 만들어 보내는 쪽, 하나는 JavaScript가 받은 response를 JSON으로 읽는 쪽입니다. 방향이 반대입니다.
- **"왜 `addEventListener()`에 함수를 바로 호출하면 안 되나요?"**
  → 호출하면 그 자리에서 실행된 **결과값**이 전달되고, event가 발생한 뒤에 실행될 function 자체가 남지 않기 때문입니다.
- **"화면 갱신은 어떻게 처리했나요?"**
  → CRUD 성공 후 `loadMovies()` / `loadTasks()`를 다시 호출해 최신 데이터를 재조회하고 DOM을 갱신했습니다. 페이지 전체 새로고침은 하지 않았습니다.
