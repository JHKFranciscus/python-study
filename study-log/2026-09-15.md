# 공부일지 · 2026-09-15

> **한 줄 요약** 코드가 실행되는 것과 요구사항을 정확히 만족하는 것은 다르다. (partial PATCH · reset)

## 오늘 한 일

- 4단계 완료 기준 마지막 확인으로, 지원 일정 관리 프로그램을 빈 프로젝트에서 Flask + MongoDB + JavaScript 전체 CRUD로 구현했다.
- optional query parameter(`stage`, `start_date`, `end_date`, `sort`) 단독·복합 조회, `nearest` / `latest` 정렬, 400 / 404, `response.ok` 확인 후 직접 `throw`하는 Promise 흐름, PATCH / DELETE 후 현재 filter 유지 재조회를 구현했다.

## 막힘 → 시도 → 배움

### ① 개념 혼동: partial PATCH와 field 검사

- **막힘** (a) PATCH에 일부 field만 들어올 수 있다는 조건을 처음 코드에 제대로 반영하지 못했고, 없을 수도 있는 field의 value에 `item[field]`로 바로 접근했다. (b) POST와 PATCH에서 존재 확인과 value 검사를 각각 언제 할지 기준이 명확하지 않았다.
- **시도** (a) 피드백 후, request에 들어온 field만 검사하고 수정하도록 고쳤다. (b) field 판단 기준을 다시 정리했다.
- **배움** (a) PATCH body에 없는 field는 오류가 아니라 이번 수정 대상이 아니라는 뜻이다. (b) field 검사는 명세에 따라 다르다. `필수인가`, `value 제한이 있는가`를 보고, 없을 수 있는 field에는 바로 접근하지 않는다.
  - 필수 + 제한 있음 → 존재 확인 + value 검사
  - 필수 + 제한 없음 → 존재 확인
  - optional + 제한 있음 → 있을 때만 value 검사
  - optional + 제한 없음 → 없으면 넘어가고, 있으면 사용

### ② 명세 놓침: reset과 화면 state

- **막힘** reset에서 `stage`를 빠뜨렸다. `sort`는 전체 조회 여부와 직접 관계없어 남겨도 된다고 생각했지만, 명세에는 filter와 sort를 모두 초기화하라고 적혀 있었다.
- **시도** 피드백 후, 모든 filter / sort state를 초기화하도록 고쳤다.
- **배움** filter DOM 값도 화면이 가진 state다. 작업 후 유지할지, reset에서 초기화할지는 내 판단이 아니라 요구사항이 정한다.

### ③ 검증 방법

- 처음 구현 후 요구사항과 코드를 다시 대조했고, 수정 후 Browser / Console에서 전체 동작을 다시 확인했다.
- `요구사항 → client request → Flask → MongoDB → HTTP response → client` 순서로 흐름을 다시 추적했다.

### 복습: HTTP status · response body · Promise

- 404는 route가 없을 때뿐 아니라 요청한 resource가 없을 때도 쓸 수 있다. 405는 path는 있지만 그 HTTP method가 허용되지 않은 경우다.
- `fetch()`는 400 / 404를 받아도 자동으로 rejected 되지 않는다. `response.ok`를 확인하고 직접 `throw`해야 `.catch()`로 간다.

## 결과: 독립 / 도움

- **직접** 빈 프로젝트에서 CRUD 큰 구조를 구성했다.
- **도움** partial PATCH와 reset은 피드백 후 오류를 확인했고, 수정 코드 일부를 그대로 복사했다. 이 부분은 독립 성공으로 볼 수 없다.
- **아직** 긴 요구사항에서 필수 / optional 여부와 state 유지·초기화 조건을 끝까지 놓치지 않고 코드에 반영하는 능력은 완전히 확인되지 않았다.

## 내일

- CRUD 전체는 다시 만들지 않고, 오늘 독립성이 확인되지 않은 partial PATCH와 state 처리만 최소 범위로 다시 확인한다.
-이런 세부 명세까지 외부 피드백 없이 구현·자체 검증 과정에서 맞추면 4단계를 끝내고 AWS 단계로 넘어간다.

**30초 스크립트**

> 4단계 마무리로 지원 일정 관리 프로그램을 빈 프로젝트에서 Flask, MongoDB, JavaScript로 만들었습니다. CRUD 큰 구조는 직접 구성했지만, 일부 field만 들어오는 PATCH와 reset은 처음에 명세대로 맞추지 못했고 피드백을 받고서야 확인했습니다. 이 과정에서 field를 '필수인가, value 제한이 있는가'로 나눠 검사 기준을 정리했고, 실행되는 코드와 요구사항을 만족하는 코드는 다르다는 걸 배웠습니다.

**예상 꼬리질문**

- 오류는 직접 고쳤나요? → 피드백 후 확인했고 수정 코드 일부는 그대로 가져다 썼다고 말한다. 그래서 그 부분만 피드백 없이 다시 확인하기로 했다고 잇는다.
- POST와 PATCH 검증은 뭐가 다른가요? → POST는 필수 / optional과 value 제한 기준대로 검사하고, PATCH는 들어온 field만 검사하고 수정한다.
- 서버가 404를 주면 `.catch()`로 가나요? → HTTP 400 / 404만으로는 fetch()가 rejected 되지 않는다. response.ok를 확인한 뒤 직접 throw하면 그 Promise chain이 rejected 되어 .catch()로 간다.
