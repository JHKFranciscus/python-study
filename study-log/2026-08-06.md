## 막힌 점

### 1) 데코레이터의 바깥 함수가 받는 값을 잘못 알았다

독립 재현에서 데코레이터의 바깥 함수가 받는 값과 실제 함수 호출 때 전달되는 값을 구분하지 못했다.
처음에는 `validate_order()`가 주문 딕셔너리를 직접 받는다고 생각했다.

```python
def validate_order(order):
    if order["price"] <= 0:
        ...
```

하지만 데코레이터가 적용되는 시점에는

```python
@validate_order
def calculate_order(order):
    ...
```

`validate_order()`에 주문 딕셔너리가 아니라 `calculate_order` 함수 객체가 전달된다.
함수 객체에 `order["price"]`처럼 접근했기 때문에 다음 오류가 발생했다.

```
TypeError: 'function' object is not subscriptable
```

### 2) wrapper를 만들어 반환하는 이유를 이해하지 못했다

일반 함수라면 함수 객체와 주문 데이터를 한 번에 전달할 수 있다.

```python
validate_order(calculate_order, order)
```

그런데 데코레이터에서는 왜 내부에 `wrapper`를 만들고 그 함수를 반환해야 하는지 바로 이해하지 못했다.

### 3) 클로저의 역할을 섞었다

성공 횟수 클로저를 처음 작성할 때, 주문 처리 결과를 받아야 하는 함수 안에서 주문 처리 함수를 다시 호출하려 했다.

### 4) 매개변수 데코레이터를 적용하고 다른 함수를 호출했다

추가 학습에서 `ship_product`를 정의한 뒤 테스트할 때 기존의 `process_product`를 다시 호출하여 배송 설정이 적용되지 않았다.

## 시도한 것

전체 프로그램을 한 번에 수정하지 않고 기능별로 분리해서 확인했다.

1. 로그 데코레이터를 제외하고 검사 데코레이터만 적용했다.
2. 정상 주문은 계산 함수까지 실행되고, 잘못된 주문은 검사 단계에서 `None`을 반환하는지 확인했다.
3. 검사 데코레이터가 정상 작동한 뒤 로그 데코레이터를 바깥쪽에 연결했다.
4. 주문 계산 함수가 원본 딕셔너리를 직접 변경하지 않고 복사본에만 `total_price`를 추가하는지 확인했다.
5. 주문 처리 결과인 딕셔너리 또는 `None`을 성공 횟수 클로저에 전달했다.
6. 책, 키보드, 마우스 주문을 차례로 처리하여 성공 횟수가 1 → 1 → 2로 누적되는지 확인했다.
7. 매개변수를 받는 데코레이터는 설정값, 원래 함수 객체, 실제 호출값을 각각 받는 단계를 나누어 실행했다.
8. 마지막 호출 대상을 `process_product`에서 `ship_product`로 수정하여 배송 설정이 정상 적용되는 것을 확인했다.

### 최종 실행 결과

| 주문 | 검사 | 처리 | 성공 주문 |
| --- | --- | --- | --- |
| 책 | 통과 | 주문 금액 계산 → 처리 완료 | 1건 |
| 키보드 | 가격 검사 실패 → `None` 반환 | 처리 실패 | 1건 유지 |
| 마우스 | 통과 | 주문 금액 계산 → 처리 완료 | 2건 |

## 배운 것

### 1) `@decorator`는 대입과 같다

```python
function = decorator(function)
```

따라서 데코레이터의 바깥 함수는 실제 주문 데이터가 아니라 꾸밀 함수 객체를 받는다.

### 2) wrapper는 값을 받는 두 시점을 연결한다

- 데코레이터 적용 시점 → 바깥 함수가 원래 함수 객체를 받는다.
- 실제 함수 호출 시점 → wrapper가 실제 데이터를 받는다.

데코레이터가 wrapper를 반환하면 원래 함수 이름에 wrapper가 저장되고, 이후 원래 함수 이름을 호출했을 때 wrapper가 먼저 실행된다.
막힌 점 2)에 대한 답이 여기에 있다. 두 시점이 다르기 때문에 한 번에 전달할 수 없고, wrapper가 그 사이를 이어 준다.

### 3) 데코레이터를 겹치면 바깥쪽부터 실행된다

```python
@log_order
@validate_order
def calculate_order(order):
    ...
```

개념적으로는 다음과 같다.

```python
calculate_order = log_order(validate_order(calculate_order))
```

따라서 실제 호출 순서는 `log_order`의 wrapper → `validate_order`의 wrapper → 원래 `calculate_order`이다.

### 4) 클로저는 값을 기억하고, 바꾸려면 `nonlocal`이 필요하다

클로저는 바깥 함수가 종료된 뒤에도 바깥 함수의 값을 기억한다.
내부 함수에서 그 값을 새로 대입하여 변경하려면 `nonlocal`이 필요하다.

### 5) 처리하는 함수와 기록하는 함수는 역할이 다르다

성공 횟수 클로저는 주문을 다시 처리하는 함수가 아니라, 이미 처리된 결과를 받아 성공 여부를 기록하는 함수다.

주문 딕셔너리 → `calculate_order()` → 처리 결과 딕셔너리 또는 `None` → `record_success()` → 성공 횟수 누적

### 6) 매개변수를 받는 데코레이터는 세 값을 서로 다른 단계에서 받는다

| 값 | 받는 시점 |
| --- | --- |
| `label` | 데코레이터에 전달한 설정값 |
| `original_function` | 꾸밀 원래 함수 객체 |
| `name` | 실제 함수 호출 때 전달되는 값 |

```python
@add_label("배송")
def ship_product(name):
    ...
```

개념적으로 다음과 같다.

```python
ship_product = add_label("배송")(ship_product)
```

## 아직 모르는 것

완성된 데코레이터 코드를 읽고 실행 흐름을 따라가는 것은 가능하다.
그러나 새로운 요구사항만 보고 다음 구조를 처음부터 독립적으로 설계하는 능력은 아직 부족하다.

바깥 함수가 원래 함수 객체를 받음 → wrapper가 실제 데이터를 받음 → wrapper가 원래 함수를 호출함 → 바깥 함수가 wrapper를 반환함

오늘 독립 재현에서는 이 구조를 직접 구성하지 못했고, 단계별 설명과 함수 틀을 받은 뒤 프로그램을 완성했다.

- 1차 독립 재현: 실패
- 보조 설명 후 재구현: 성공
- 최종 프로그램 실행: 성공

매개변수를 받는 데코레이터도 단계별 안내를 받아 작성했으므로, 독립적으로 재현할 수 있는 상태는 아니다.
