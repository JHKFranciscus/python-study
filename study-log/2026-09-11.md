# 공부일지 — PATCH 부분 수정과 record별 수정 흐름

**한 줄 요약** — request에 실제로 들어온 field만 골라 수정하는 PATCH를 익히고, 각 record가 자기 input과 `_id`를 가지는 수정/삭제 화면을 직접 구성했다.

**키워드** — `if field in data` · `$set` · `matched_count`/`modified_count` · 400 vs 404 · path/query/body · ObjectId 변환

---

## 1. PATCH — 있는 field만 고치기

- request에 포함된 field만 update dictionary에 담아 `$set`으로 넘기는 구조를 학습했고, 기존 독서 기록 CRUD에 title / category / read_date / pages 다중 field PATCH를 결합했다.
- `if field in data`로 key 존재 여부와 value의 truthy/falsy를 구분했다.

**막힌 점 → 해결**

1. request에 없는 field를 서버에서 `None`으로 다시 만들어 `$set`할 수 있는 구조였다 → request에 실제로 들어온 key만으로 update dictionary를 만들었다.
2. number input의 빈 string에 `Number()`를 먼저 적용해 `0`이 됐다 → 원래 string value를 먼저 확인하고 필요할 때만 변환했다.
3. PATCH category validation을 빠뜨렸다 → validation을 추가했다.

**배운 점** — PATCH에서는 **value가 비어 있는 것과 field 자체가 request에 없는 것을 구분해야 한다.**

## 2. 결과 판별과 error 응답

- `matched_count`와 `modified_count`의 차이를 확인했다.
- 잘못된 ObjectId는 400, 형식은 정상이지만 document가 없으면 404로 구분했다.

**막힌 점 → 해결**

4. resource가 없는 경우를 처음에 400으로 처리했다.
5. 잘못된 ObjectId response에 400 status를 붙이지 않았다 → 4와 함께 형식 오류(400)와 미존재(404)로 분리했다.
6. Flask error response의 key와 JavaScript에서 읽는 property가 맞지 않았다 → 양쪽 이름을 맞췄다.

**배운 점** — `matched_count == 0`은 resource가 없다는 뜻이지만, `modified_count == 0`은 **기존 값과 새 값이 같아 변경이 없었을 때도** 나온다.

## 3. 값이 지나가는 길

- JavaScript input → object → `JSON.stringify()` → Flask `request.get_json()` → MongoDB `$set` 흐름을 연결했다.
- `_id`가 `ObjectId → Python str → JavaScript string → URL path → Python str → ObjectId`로 바뀌는 흐름을 추적했다.
- path parameter / query parameter / request body의 위치와 Flask에서 읽는 방법을 구분했다.

**배운 점** — 이름이 비슷하다고 client와 server가 자동으로 이어지지 않는다. 세 위치를 각각 직접 연결해야 한다.

## 4. 독립 재현 — 공부 세션 관리 페이지

**직접 한 것**

- 기존의 공용 수정 input 방식과 달리, 각 record가 자기 수정 input과 `_id`, 수정/삭제 버튼을 가지는 구조를 직접 구성했다.
- 수정/삭제 후 현재 subject / 날짜 범위 / sort 상태를 유지한 채 재조회하도록 연결했다.
- 수정 후 전체 요구사항을 브라우저에서 테스트했다.

**피드백으로 고친 것**

7. optional `sort`가 없을 때도 invalid sort로 처리되는 조건을 썼다 → 값이 있을 때만 validation하도록 고쳤다.
8. JavaScript 변수를 선언하지 않고 사용했다 → (해결 과정은 따로 기록하지 않았다.)

**평가** — 큰 구조는 직접 구성했지만 세부 오류는 피드백으로 고친 뒤 동작을 확인했다. **완전 독립 성공으로 기록하지 않는다.** 반복된 오류 유형은 optional 값 존재 여부 / type 변환 시점 / HTTP status / response key와 client property / validation 누락 / 없는 field 처리다.

## 5. 내일

- 오늘 오류만을 이유로 별도 보충일을 만들지 않고 다음 본 진도로 간다.
- 본 진도 안에서 현재 value / type / 이름 / 전달 위치를 짧게 추적한다.
- 오늘 SSAFY는 생략했다.

## 부록 — 면접용

**30초 스크립트**

"Flask와 MongoDB로 CRUD를 만들면서 PATCH를 붙였는데, 처음에는 요청에 없는 field까지 서버에서 None으로 만들어 덮어쓸 수 있는 구조였습니다. 그래서 요청에 실제로 들어온 key만 모아 update dictionary를 만들고 $set에 넘기도록 바꿨습니다. 결과 판별도 잘못된 ObjectId는 400, 형식은 맞지만 문서가 없으면 404로 나눴습니다. 이어진 재현 과제에서는 각 record가 자기 input과 _id를 가지는 수정 화면을 직접 구성했고, 세부 오류는 피드백을 받아 고친 뒤 브라우저에서 전체 동작을 확인했습니다."

**예상 꼬리질문**

- modified_count가 0이면 실패인가요? → 아니다. 값이 같으면 변경이 없어도 0이 나오고, 존재 여부는 matched_count로 본다.
- 왜 400과 404를 나눴나요? → 잘못된 ObjectId는 요청 형식 문제, document 미존재는 대상 문제라서 구분했다고 답한다.
- PATCH와 PUT의 차이는? → 오늘 기록에는 PUT 비교가 없다. 부분 수정 경험만 말하고 비교는 확인 후 답한다.

**아직 빈 칸** — PUT과의 비교, validation 공통화 방법, 피드백을 준 도구/사람은 기록에 없다.
