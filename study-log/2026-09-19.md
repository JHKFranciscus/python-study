# 2026-09-19 — 운영 중인 Flask application 재배포

**한 줄 요약**
이미 운영 중인 Flask application의 code를 수정해 EC2에 재배포하면서, `git pull`은 file을 바꾸고 `systemctl restart`는 process를 바꾼다는 차이를 PID로 직접 확인했다.

**키워드 앵커**: 재배포 / file vs process / PID / port / 장애 위치 판단

---

## 1. 오늘 한 일

어제까지 만든 운영 구조는 그대로 두고, 그 위에 새 version을 올리는 재배포만 진행했다.

운영 구조
Browser → Nginx :80 → Gunicorn 127.0.0.1:5000 → Flask → MongoDB

시작 상태 확인
- mongod / flask-study / nginx 모두 active, enabled
- ss: Nginx 0.0.0.0:80, Gunicorn 127.0.0.1:5000 LISTEN
- `curl http://127.0.0.1:5000/`, `curl http://127.0.0.1/` 모두 Flask HTML 반환

실제로 수행한 재배포 흐름
local code 수정 → 변경 확인 → commit → push → EC2 git pull → flask-study restart → EC2 내부 curl 검증 → 외부 browser 검증

재배포가 실제로 적용됐는지 눈으로 확인하려고 HTML title을 `지원 일정 관리 프로그램` → `지원 일정 관리 프로그램 - redeploy`로 바꿨다. 새 commit은 `032cd11 fix deployed app references and redeploy`이고, EC2의 HEAD도 같은 commit으로 맞췄다.

---

## 2. 막힌 점 → 시도 → 배운 점

### ① EC2의 working tree가 clean하지 않았다
- **막힌 점**: git status에 modified `app2.py`, `app2.html`, untracked `~venvs/`가 남아 있었다. 이전 배포 때 EC2에서 직접 고친 `app1.html → app2.html`, `app1.js → app2.js` 수정이 EC2에만 있었다. EC2의 main은 GitHub보다 3 commits 뒤였다.
- **시도**: 바로 git pull 하지 않고 변경 내용을 먼저 확인했다. 같은 수정을 local repository에 반영해 commit·push한 뒤, EC2에 남아 있던 직접 수정본을 정리하고 최신 commit을 가져왔다.
- **배운 점**: 서버에서 직접 고친 code는 기록이 남지 않아 다음 배포에서 걸린다. 정본은 GitHub에 두고 EC2는 pull로만 맞춰야 한다.

### ② git pull을 해도 화면이 바뀌지 않을 수 있다
- **막힌 점**: pull로 disk의 code file은 최신이 됐지만, 실행 중인 Gunicorn process가 새 code를 자동으로 다시 읽는 것은 아니었다.
- **시도**: `sudo systemctl restart flask-study`를 실행하고 PID를 비교했다. restart 전 525, 789 → restart 후 4337, 4338.
- **배운 점**: restart는 file을 바꾸는 게 아니라 **기존 process 종료 → 새 process 시작**이다. 그래서 git pull은 file 변경, systemctl restart는 process 변경으로 나눠서 봐야 한다.

### ③ 127.0.0.1:5000을 process처럼 표현했다
- **막힌 점**: 설명할 때 127.0.0.1:5000 자체를 process라고 말했다.
- **시도**: 127.0.0.1은 address, 5000은 port, Gunicorn은 그 port를 LISTEN하는 process로 교정했다.
- **배운 점**: 새 Gunicorn process도 같은 127.0.0.1:5000을 LISTEN하므로 Nginx의 proxy_pass는 손댈 필요가 없었다. Nginx는 특정 PID를 찾아가는 게 아니라 127.0.0.1:5000으로 request를 넘기기 때문이다.

## 3. 오늘 확실히 구분한 것

- `app2.py` → disk에 저장된 code file
- Gunicorn → Flask application을 실행하는 process
- PID → 실행 중인 각 process를 식별하는 ID
- 5000 → Gunicorn이 network request를 받는 port

---

## 4. 장애 위치 판단과 검증

- 127.0.0.1:5000 실패 → flask-study / Gunicorn 쪽
- 5000 성공, 127.0.0.1:80 실패 → Nginx 쪽
- EC2 내부 :80 성공, 외부 browser 실패 → Public IPv4 / Security Group / 외부 network

오늘 검증도 이 순서 그대로 했다. `curl :5000` → `curl :80` → Windows browser(Public IPv4). 세 곳 모두 바뀐 title이 나왔고, 기존 MongoDB data도 그대로 조회됐다.

## 5. 독립성 구분

**독립적으로 한 것**
- 재배포 전 세 service 상태, ss, curl로 시작 상태 확인
- git status를 통해 EC2 working tree가 clean하지 않은 상태를 직접 확인
- local 수정 → commit → push → EC2 pull → restart 실제 수행
- restart 전후 PID 비교로 process 교체 확인
- 3단계 검증(curl :5000 → curl :80 → 외부 browser)

**교정·안내를 받은 것**
- 예상하지 못한 Git working tree 상태를 확인·정리하는 과정의 일부 명령(fetch, origin/main, diff 비교)
- 재배포 전체 순서를 처음에는 바로 독립 재현하지 못했고, 교정 후에 다시 재현했다
- 127.0.0.1:5000 표현 교정

→ 따라서 AWS/Linux와 Git을 완전히 독립적으로 운영할 수 있는 수준으로 보지는 않는다.

## 6. SSAFY

오늘 SSAFY는 개인 사정으로 진행하지 않았다. 명시적 PASS이며 실패, 미완료, 진도 부족, 다음 날 이월로 처리하지 않는다.

# 면접 부록

## 30초 구두 스크립트

"EC2에 Nginx, Gunicorn, Flask, MongoDB로 올려둔 application을 수정해서 재배포한 경험이 있습니다. 배포 전에 서버의 working tree가 깨끗하지 않은 것을 발견해서, 바로 pull하지 않고 변경 내용을 먼저 확인한 뒤 local에 반영해 push하고 서버는 pull로 맞췄습니다. pull로 EC2의 code file은 최신 상태가 되었지만, 실행 중인 Gunicorn process가 새 code를 자동으로 다시 읽는 것은 아니기 때문에 service restart가 필요하다는 점을 이해했습니다. service를 restart한 뒤 PID가 525, 789에서 4337, 4338로 바뀐 것을 보고 process가 실제로 교체된 것을 확인했고, Gunicorn에 직접 curl, Nginx를 통한 curl, 외부 browser 순서로 세 단계로 검증했습니다."

## 예상 꼬리질문과 답변 방향

- **"왜 서버에서 직접 고치면 안 됩니까?"** → 기록이 남지 않아 다음 pull에서 걸린다. 이번에 실제로 그 상태를 마주했고 local·GitHub에 반영한 뒤 서버를 맞추는 방식으로 정리했다고 답한다.
- **"pull만 하고 restart를 안 하면 어떻게 됩니까?"** → disk의 file은 최신이지만 실행 중인 process는 이전 code를 들고 있어서 응답이 바뀌지 않는다고 답한다.
- **"restart하면 Nginx 설정도 바꿔야 합니까?"** → 새 process도 같은 127.0.0.1:5000을 LISTEN하므로 필요 없고, Nginx는 PID가 아니라 port로 전달한다고 답한다.
- **"배포가 잘못되면 어디부터 봅니까?"** → curl :5000 → curl :80 → 외부 browser 순서로 범위를 좁힌다고 답한다.
- **"Git은 어느 정도 다룹니까?"** → 기본 흐름은 직접 하지만 예상 못 한 working tree 상태를 정리할 때는 아직 안내를 참고했다고 솔직하게 답한다.

## 아직 빈틈 (면접 전 채울 것)

- restart 동안 서비스가 잠깐 끊겼는지 확인하지 않았다. 무중단 배포 개념과 연결해 둘 것.
- 재배포가 잘못됐을 때 되돌리는 rollback을 아직 해보지 않았다.
- untracked였던 `~venvs/`를 결국 어떻게 처리했는지 기록에 없다. (.gitignore 처리 여부 확인 필요)
- fetch / origin/main / diff 비교를 다음에는 안내 없이 쓸 수 있는지 한 번 더 확인할 것.
