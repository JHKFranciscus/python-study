## 2. 막힌 것 → 대조한 것 → 배운 것

큰 CRUD 구조와 row 단위 수정 data flow는 직접 구성했지만 첫 구현에는 세부 오류가 있었다.

피드백을 받은 뒤 실행 여부만 다시 보지 않고, 요구사항과 실제 코드가 같은 의미인지 항목별로 대조했다.

### (1) sort 계약

- 막힌 것: `nearest` / `latest`의 sort 방향을 반대로 작성했다.

- 막힌 것: `sort`가 optional인데도 `sort`가 없는 경우를 처음에는 별도로 처리하지 못했다.

- 대조: `nearest` / `latest` 요구사항과 실제 `date` sort 방향을 비교했다.

- 배운 것: 코드가 실행된다는 것만으로 요구사항을 만족했다고 판단할 수 없다.

### (2) optional field

- 막힌 것: PATCH에서 optional field인 `room`의 존재 여부를 확인하기 전에 value에 접근했다.

- 대조: PATCH body에 field가 없을 수 있다는 조건과 server의 field 접근 방식을 비교했다.

- 배운 것: optional field는 존재 여부를 먼저 판단한 뒤 value를 사용해야 한다.

### (3) HTTP status 계약

- 막힌 것: 존재하지 않는 PATCH 대상에 400을 반환했다.

- 막힌 것: DELETE 대상이 없을 때 response body만 만들고 404 status를 지정하지 않았다.

- 대조: 잘못된 request와 존재하지 않는 resource를 구분해 400 / 404를 다시 확인했다.

- 배운 것: HTTP error body와 HTTP status는 별개다.

### (4) Promise 흐름

- 막힌 것: `response.ok === false`일 때 error 값을 return만 해서 Promise가 rejected 되지 않았다.

- 대조: `response.ok` 이후 `throw`가 있어야 rejected 흐름으로 넘어가는 것을 확인했다.

- 배운 것: `fetch()`는 400 / 404만으로 자동 rejected 되지 않는다.

그 외 `console.log` 오타 1건을 수정했다.

수정 후 browser와 Console 검증은 모두 통과했고, filter를 초기화하지 않고 현재 DOM value를 그대로 사용해 PATCH / DELETE 후 재조회되는지도 함께 확인했다.

## 3. 오늘의 대표 포인트

`client request → Flask 처리 → MongoDB operation → HTTP response → 다시 client 처리`

까지 같은 의미로 이어지는지 확인해야 한다.

## 4. 아직 부족한 부분

CRUD의 큰 구조를 구성하는 것 자체보다, 코드가 길어졌을 때 다음 조건들을 피드백 없이 끝까지 일관되게 유지하는 정확도가 부족하다.

- optional field
- sort 기준과 방향
- API 계약
- HTTP status
- Promise 흐름
- 작업 후 유지하거나 초기화해야 하는 state

오늘도 큰 구조는 직접 구성했지만 이 부분들은 피드백 후 수정했으므로 완전 독립 성공으로 보기는 어렵다.

## 부록: 면접용

### 30초 구두 스크립트

회의실 예약 CRUD를 빈 프로젝트에서 직접 구현했습니다. Flask와 MongoDB, JavaScript로 POST, GET, PATCH, DELETE를 만들고, 조건 조회와 정렬을 optional query parameter로 처리했습니다. 첫 구현에서는 정렬 방향이나 400과 404 구분 같은 세부 계약이 어긋나 있었는데, 실행되는지만 보지 않고 요구사항과 코드를 항목별로 대조해서 고쳤습니다. 이 과정에서 요청부터 응답까지 같은 의미로 이어지는지를 확인해야 한다는 기준을 잡았습니다.

### 예상 꼬리질문과 답변 방향

- **"그 오류들을 스스로 찾았나?"**  
  구조와 data flow는 직접 구성했고, 세부 계약 오류는 피드백을 받은 뒤 요구사항과 코드를 대조해 고쳤다고 그대로 말한다. 포장하지 않는다.

- **"400과 404를 어떻게 구분했나?"**  
  잘못된 request는 400, 존재하지 않는 resource는 404라고 구분했다. response body만 만들고 status를 지정하지 않았던 실수를 예로 든다.

- **"fetch 에러 처리는?"**  
  `response.ok`가 false일 때 값을 return만 하면 rejected 되지 않으므로 `throw`가 필요하다고 설명한다.

- **"수정 대상은 어떻게 특정했나?"**  
  row 안에서 `_id`와 현재 DOM value를 함께 얻을 수 있어 별도 `editingId` state 없이 결정했다고 설명한다.

### 면접 전 확인할 사항

- 구현과 수정에 각각 걸린 시간은 별도로 측정하지 않아 현재 기록 없음.

- 같은 회의실의 동일 시간대 중복 예약 검증은 이번 구현 요구사항에 포함하지 않음.

- sort 동작:
  - sort 미지정 → 별도 sort를 적용하지 않음
  - `nearest` → `date` 오름차순
  - `latest` → `date` 내림차순

- 이번 구현에서 400으로 처리한 경우:
  - POST 필수 field 부재
  - POST 필수 field가 빈 string
  - POST의 invalid room
  - PATCH의 invalid room
