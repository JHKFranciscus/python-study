## 오늘 한 일

### 1. 8주차 개념 복습

Flask의 `request → route → 함수 실행 → 데이터 처리 → return → response` 흐름을 다시 설명했다.

이어서 동적 URL과 함수 parameter의 연결, GET/POST의 form 데이터 전달 방식, `request.args`와 `request.form`의 차이, Jinja와 JavaScript의 실행 위치, 서버 메모리와 서로 다른 request의 관계를 확인했다.

### 2. 독립 재현 1차 — 할 일 관리 (성공으로 처리하지 않음)

서버 메모리의 할 일을 조회·추가·변경하는 프로그램을 만들었다. 기능 자체는 최종적으로 동작했다.

다만 두 가지 이유로 독립 재현 성공으로 처리하지 않았다.

1. JavaScript/Ajax를 사용하지 않는다는 조건을 지키지 못했다.
2. 여러 오류를 **외부 검수를 받은 뒤에** 수정했다.

### 3. 독립 재현 2차 — 점수 관리 (1차 막힘 후 조건대로 완성)

구조가 다른 문제로 다시 재현했다. 이번에는 JavaScript 없이 Flask, HTML form, GET/POST, `request.args`, `request.form`, Jinja, 서버 메모리만 사용했다.

구현한 기능은 전체 목록 표시, 새 사용자 추가, 기존 점수 수정, 특정 사용자 검색이다.

### 4. CS 복습

URL의 구성, 404·405·연결 실패의 차이, origin과 port, 서로 다른 request와 서버 메모리의 관계를 다시 확인했다.

### 5. 주간 정리

8주차 전체 내용을 주간 블로그 초안으로 정리했다.

## 막힌 것 → 시도한 것 → 배운 것

### 1. JavaScript 함수의 parameter 이름으로 `this`를 써서 SyntaxError가 났다

**막힌 것**
파일 전체가 실행되지 않아서 여러 기능이 동시에 고장 난 것처럼 보였다. 원인이 한 곳이라는 걸 바로 알아채지 못했다.

**시도한 것**
HTML의 `id`·`name`, JavaScript selector, JSON key처럼 서로 연결되는 이름을 하나씩 대조했다.

**배운 것**
HTML에서 `this`를 함수 호출의 argument로 넘길 수는 있다. 하지만 JavaScript 함수의 parameter 이름으로 `this`를 쓸 수는 없다.

### 2. 1차 구현이 문제에서 요구한 조건을 벗어났다

**막힌 것**
HTML·JavaScript·Flask 사이의 연결 지점을 여러 번 혼동했고, 결과적으로 JavaScript를 쓰지 않는다는 조건도 지키지 못했다.

**시도한 것**
이전 구현을 고치지 않았다. JavaScript 파일을 제거하고 Flask + HTML form + Jinja만 쓰는 구조로 새로 설계했다.

**배운 것**
독립 재현은 기능이 동작하는 것만으로 끝나지 않는다. **문제에서 요구한 범위와 구조를 지키는 것까지가 조건이다.**

### 3. `/search`에서 `scores is undefined`가 났다

```text
jinja2.exceptions.UndefinedError: 'scores' is undefined
```

**막힌 것**
`/`에서는 잘 나오던 화면이, `/search`에서 같은 HTML template을 다시 렌더링하니 오류가 났다.

**시도한 것**
`/`와 `/search`에서 각각 호출한 `render_template()`을 나란히 놓고 비교했다.

**배운 것**
`render_template()`에 넘긴 변수는 다른 request의 렌더링까지 자동으로 유지되지 않는다. **서버 메모리에 데이터가 남아 있는 것과, 그 데이터를 Jinja에 전달하는 것은 별개의 과정이다.**

### 4. CS 개념 두 개를 정확하게 설명하지 못했다

**막힌 것**
상대경로 `/add`가 왜 Live Server의 5500번 port로 가는지, 서로 다른 request가 왜 변경된 서버 메모리를 함께 볼 수 있는지 설명하지 못했다.

**시도한 것**
요청 흐름을 처음부터 다시 따라가면서 origin과 서버 프로세스의 메모리 지속을 구분했다.

**배운 것**

- 상대경로는 브라우저가 **현재 페이지의 origin**을 기준으로 해석한다. 그래서 Live Server 5500에서 연 페이지의 `/add` 요청은 Flask 5000으로 자동으로 가지 않는다.
- 서로 완전히 다른 HTTP request라도, Flask 서버 프로세스가 계속 실행 중인 동안에는 그 프로세스의 메모리에 있는 같은 데이터를 쓸 수 있다.

## 아직 부족한 부분

HTML, Jinja, JavaScript, Flask가 동시에 연결될 때 서로 대응하는 이름을 한 번에 추적하는 능력이 아직 안정적이지 않다.

Jinja는 서버에서 Response가 만들어지기 전에 실행되고, JavaScript는 브라우저가 Response를 받은 뒤에 실행된다. 이 차이는 설명할 수 있지만 실제 구현에서는 문법이나 역할을 섞을 가능성이 있다.

기능을 만들 때 현재 요구사항보다 복잡한 구조를 선택하는 경우가 있다. 코드를 쓰기 전에 가장 단순한 요청 흐름부터 설계하는 연습이 필요하다.
