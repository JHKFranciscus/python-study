## 2. 배포에서 만난 문제

### ① 상태 불일치 — file은 최신인데, 실행 중인 건 이전 application

- **상황** EC2 repository를 최신 commit으로 맞춘 뒤, `flask-study.service`가 이전 application을 실행하고 있다는 것을 확인했다.
- **조치** service를 이번 application에 맞게 두 군데 고쳤다.
  - `WorkingDirectory` : `day0072/f2` → `day0079/f1`
  - Gunicorn target : `app2:app` → `app1:app`
- **배운 점** "최신"은 세 단계로 나뉜다. service 파일 자체를 바꿨다면 `daemon-reload → restart`까지 해야 한다.

```
push    → GitHub 최신
pull    → EC2 disk 최신
restart → 실행 process 최신
```

### ② 개념 혼동 — `203/EXEC`

- **증상** service 수정 후 `flask-study`가 `failed`. `systemctl status`에서 `status=203/EXEC`를 확인했다.
- **원인** `ExecStart`의 Gunicorn 경로까지 새 application에 맞춰 바꿔 버렸다. application이 `day0079/f1`에 있다고 Gunicorn 실행 파일도 거기 생기는 건 아니다.
- **해결** 실제로 존재하는 기존 virtual environment의 Gunicorn 경로로 되돌림 → `daemon-reload → restart → active` 확인
- **이번 배포에서는** application이 바뀌었으므로 `WorkingDirectory`와 Gunicorn target만 변경하면 됐고, 기존 virtual environment의 Gunicorn 실행 파일 경로는 유지해야 했다.

```
1. WorkingDirectory → 어디서   : application이 있는 directory
2. .../bin/gunicorn → 무엇으로 : 실제 Gunicorn 실행 파일
3. app1:app         → 무엇을   : Python module(app1) 안의 Flask 객체(app)
```

**30초 스크립트**

> 첫 웹 모의시험에서 Flask로 만든 시설 장애 신고 관리 서비스를 AWS EC2에 배포했습니다. systemd service를 수정한 뒤 203/EXEC 오류로 서비스가 failed 상태가 됐는데, 원인은 새 application에 맞춰 Gunicorn 실행 파일 경로까지 바꿔 버린 것이었습니다. 실제 virtual environment의 Gunicorn 경로로 되돌리고 daemon-reload 후 restart해서 복구했고, curl로 Gunicorn과 Nginx 구간을 나눠 확인한 뒤 외부 browser에서 CRUD 전체를 검증했습니다. 이 과정에서 실행 위치, 실행 파일, 실행 대상은 서로 다른 설정이라는 걸 구분하게 됐습니다.

**예상 꼬리질문**
- **203/EXEC는 무슨 뜻인가요?** → systemd가 `ExecStart`에 적힌 실행 파일을 실행하지 못했다는 뜻. 경로가 틀려 파일이 없거나 실행 권한이 없을 때 주로 난다. 이번엔 Gunicorn 경로를 잘못 바꾼 게 원인이었다.
- **code를 최신으로 맞췄는데 왜 이전 application이 실행됐나요?** → pull은 disk의 file만 바꾼다. 실행 중인 process는 restart해야 바뀌고, service 파일을 고쳤다면 daemon-reload도 필요하다. 이번엔 service가 이전 directory(`day0072/f2`)를 가리키고 있어서 service 설정부터 바꿔야 했다.
- **혼자 해결했나요?** → CRUD 골격과 흐름은 독립 구현했고, Day 1 validation 일부와 systemd 수정 과정 일부는 도움을 받았다고 그대로 말한다.
