## 한 줄 요약

Flask에서 CRUD의 Update와 Delete를 직접 구현하고, 상태 변경 뒤에는 redirect를 거쳐 새로운 GET이 발생하는 흐름까지 확인했다. 다만 데이터 구조가 바뀌었을 때 식별값이 어디 있는지 스스로 판단하는 건 아직 부족했다.

---

## 오늘 한 일

**1. Flask CRUD의 수정과 삭제 구현**

- 기존 데이터를 조회해 수정 form의 초기값으로 보여줬다.
- POST로 전달된 값을 기존 dictionary에 반영한 뒤 상세 페이지로 redirect했다.
- 삭제는 URL의 식별값으로 대상을 찾아 실제 데이터에서 제거하고, 목록 페이지로 redirect했다.
- 존재하지 않는 데이터를 요청했을 때는 404 status code도 직접 반환했다.

**2. 필수 7 — 요구사항만 보고 새로 구현**

- 학습 자료 관리 기능을 목록, 상세, 수정, 삭제, 404까지 직접 연결했다.
- 처음에는 수정·삭제 후 `render_template()`을 썼지만, 상태 변경 뒤에는 redirect를 거쳐 새로운 GET request가 발생하도록 고쳤다.

**3. 필수 8 — 구조가 다른 독립재현**

- list 안의 dictionary가 아니라 dictionary 안의 dictionary 형태로 할 일 관리 기능을 구현했다.
- 등록은 직접 구현했다.
- 기존 항목의 완료·삭제 처리는 바깥 dictionary의 key를 식별값으로 쓰는 판단과 동적 route 연결에서 막혀서, 안내를 받은 뒤 완성했다.

**4. CS**

- HTTP의 stateless와 Flask 프로세스 메모리를 구분했다.

## 막힌 부분

1. CRUD 각각의 코드는 구현할 수 있었지만, 요구사항만 보고 전체 흐름을 스스로 설계할 때는 아직 혼동이 있었다.
2. `/books/3/edit`의 `3`을 query string으로 잘못 판단했다.
3. 수정 POST와 redirect 이후의 상세 GET을 하나의 request처럼 섞어서 생각했다.
4. 데이터 구조가 dictionary 안의 dictionary로 바뀌자, 기존 list 방식처럼 대상을 다시 찾아야 한다고 생각했다. `python`, `flask`, `http`가 이미 바깥 dictionary의 key이자 식별값이라는 점을 바로 활용하지 못했다.

## 시도한 것 (막힌 부분과 같은 번호)

1. 필수 7에서 이전 코드를 복사하지 않고 학습 자료 관리 기능을 새로 만들면서, 요구사항에서 필요한 route와 흐름을 직접 뽑아 연결했다.
2. 수정·삭제를 직접 구현하면서 실제로 데이터가 변경되는 시점을 확인했고, 대상은 URL의 식별값으로 찾고 바뀔 값은 `request.form`에서 읽는다는 걸 구분했다.
3. 잘못 쓴 `render_template()`을 `redirect()`로 고쳐서 POST → 302 → 새로운 GET 흐름까지 확인했다.
4. 처음에는 dict 안의 dict 접근에서 막혔고, 안내를 받은 뒤 `tasks[task_id]`로 원하는 객체에 바로 접근할 수 있다는 점을 확인하고 나서 완료 상태 변경과 삭제를 구현했다.

## 배운 점

**CRUD는 데이터가 바뀌는 시점으로 판단한다**

함수 이름이나 HTTP method만 보고 구분하는 게 아니라, 서버 데이터가 실제로 어떻게 변하는지를 기준으로 판단해야 한다.

**Update와 Delete가 실제로 일어나는 순간이 따로 있다**

`request.form`에서 값을 읽는 것만으로 Update가 되는 게 아니라, 기존 데이터에 새 값을 대입할 때 Update가 발생한다. Delete도 대상을 찾는 게 아니라 실제 저장 구조에서 제거할 때 발생한다.

**데이터가 들어오는 위치는 서로 다르다**

동적 route 값, query string, request body는 각각 다른 위치의 데이터다.

**stateless와 Flask 프로세스 메모리는 다른 얘기다**

HTTP request들은 서로 독립적이지만, Flask 프로세스가 살아 있는 동안에는 Python 메모리의 데이터가 유지될 수 있다. 그래서 redirect 이후 발생한 새로운 GET에서도 이전 POST에서 수정한 값을 다시 읽을 수 있었다.
