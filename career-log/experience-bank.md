## 2026-07-08 조건식 오류 수정

### 상황
시험 점수와 출석률을 각각 정수로 입력받고
int(), input(), if ,elif ,else ,and ,or을 사용하여
점수 또는 출석률이 0 미만이거나 100 초과이면
잘못된 입력입니다.
점수가 70 이상이고 출석률이 80 이상이면
수료입니다.
그 외에는
미수료입니다.
위 조건을 만족하는 수료 판정 프로그램을 작성했다.

### 문제
점수 105, 출석률 90을 입력했을 때
잘못된 입력이 아니라 수료라고 출력됐다.

### 내가 처음 시도한 방법
두 변수의 범위를 한꺼번에 검사하려고 (score or check_rate) < 0 and (score or check_rate) > 100을 사용했다.

### 잘못된 이유
`score or check_rate`는 두 변수를 모두 검사하는 표현이 아니었다.
두 값 중 참으로 취급되는 한 값을 반환하므로, 각 변수의 범위를 따로 비교하지 못했다.

또한 하나의 값이 동시에 0보다 작고 100보다 클 수 없으므로
`값 < 0 and 값 > 100` 조건은 항상 거짓이었다.

### 수정한 방법
score와 check_rate를 각각 비교하도록 조건식을 score < 0 or score > 100 or check_rate < 0 or check_rate > 100으로 수정함.
점수 85·출석률 105, 점수 85·출석률 -1을 입력해 다시 확인함.

### 결과
점수 85·출석률 105와 점수 85·출석률 -1을 입력했을 때
모두 `잘못된 입력입니다.`가 출력되는 것을 확인했다.
정상 범위의 입력에서는 수료와 미수료도 기준에 맞게 출력됐다.

### 이 경험에서 배운 점
여러 변수의 범위를 검사할 때는 변수마다 비교식을 따로 작성해야 한다.
코드가 실행된다는 것만으로 맞다고 판단하지 말고,
105, -1 같은 잘못된 입력과 경계값을 직접 넣어 확인해야 한다.

## 2026-07-11 - 통계 변수의 초기화 위치를 수정한 경험

### 1. 상황

### 3. 행동

scores와 total이 각각 언제까지 값을 유지해야 하는지 비교했다.

```python
def get_book_by_index(books, index):
    return books[index]
```

- 관리 클래스가 직접 가격을 바꾸는 것이 아니라, 검색한 상품 객체의 `change_price()`를 호출해야 한다는 것을 다시 확인했다.

### 수정한 방법
```python
def change_product_price(self, target_name, new_price):
    change_product = self.find_product(target_name)
    if change_product is not None:
        return change_product.change_price(new_price)
    return False
```

검색 실패 여부는 `None`으로 확인하고, 가격 변경 작업의 성공 여부는 `True`와 `False`로 반환하도록 역할을 나눴다.

### 실제 결과
존재하지 않는 상품의 가격 변경을 시도했을 때 오류가 발생하지 않고 `False`가 반환됐다. 기존 상품의 가격도 바뀌지 않았다.

### 배운 점
같은 '실패'처럼 보여도 메서드의 역할에 따라 반환값의 의미가 다르다. 객체 검색 실패에는 `None`, 변경이나 삭제 같은 작업 실패에는 `False`를 사용한다. 그리고 호출하는 쪽에서는 그 메서드의 반환 규칙에 맞춰 조건을 작성해야 한다.

결과적으로 `load_from_file()`은 파일 읽기와 등록만, 분리한 함수는 상품 종류 판단과 객체 생성만 담당하게 됐습니다.

## 2026-08-04 경험 후보 - 서버 점검 generator에서 반복 대상과 조건 판단 오류를 수정한 경험

### 한 줄 요약

서버 점검 기록을 generator로 처리하다 오류가 났는데, 정리해 보니 세 건의 원인이 하나였다. 서버 점검 기록을 generator로 처리하는 독립 재현에서 반복 변수 `check`를 현재 서버 기록이 아니라 iterator처럼 잘못 다뤘고, 출력과 조건식에서도 현재 요소 대신 고정값과 기준값을 사용해 오류가 발생했다.
### 상황

- iterable, iterator, generator의 기본 동작을 학습한 뒤 서버 점검 기록을 새로운 문제로 적용했다.
- iterator로 점검 기록을 한 건씩 처리하고, generator로 응답 시간이 기준 이상인 서버만 생성해야 했다.

### 문제

처음 작성한 generator 코드에서 오류가 발생했다.

**단순 오타 (1건)**

- `yield`를 `yeild`로 잘못 작성해 `SyntaxError`가 발생했다.

**반복 대상과 조건 판단 오류 (3건)**

- `for check in checks`로 이미 딕셔너리 한 건을 꺼냈는데 다시 `next(check)`를 호출했다. → `check`를 iterator로 봤다.
- 현재 서버 이름 대신 `"인증 서버"`를 고정 출력했다. → 현재 요소 대신 고정값을 썼다.
- `check["response_time"]`과 `standard`를 비교해야 했는데 `standard >= 300`으로 작성했다. → 현재 데이터 대신 기준값만 검사했다.

### 확인 과정

1. 오류가 발생한 줄을 확인했다.
2. 반복문 안의 `check`에 실제로 어떤 값이 들어오는지 다시 확인했다. `check`는 iterator가 아니라 이미 꺼낸 서버 기록 딕셔너리였다.
3. 조건식이 현재 기록의 응답 시간을 검사하지 않고 기준값 자체만 검사하고 있다는 점을 구분했다.

### 수정

- `yeild` → `yield`
- `next(check)` → 제거
- `"인증 서버"` 고정 출력 → `check["server"]`
- `standard >= 300` → `check["response_time"] >= standard`

### 결과

- 응답 시간이 300ms 이상인 결제 서버와 로그 서버만 생성됐다.
- 첫 번째 느린 서버는 `next()`로 처리하고, 남은 느린 서버는 같은 generator를 `for`문으로 이어서 처리했다.
- 다만 처음부터 독립적으로 완성한 것은 아니다. 오류 원인과 수정 방향을 확인한 뒤 정상 실행까지 완료했다.

### 배운 기준

- 세 오류는 모두 반복 변수 `check`의 역할을 정확히 사용하지 못한 데서 나왔다. `check`는 이미 현재 서버 기록 딕셔너리인데 iterator처럼 다뤘고, 출력과 조건식에서는 현재 요소 대신 고정값과 기준값만 사용했다.
- `for 변수 in iterable`에서 변수에는 이미 현재 요소가 들어온다. 그 변수에 다시 `next()`를 쓰지 않는다.
- 조건식에는 기준값뿐 아니라 실제로 검사하려는 현재 데이터가 포함되어야 한다.
- generator는 같은 객체를 계속 사용하면 이전 `yield`의 실행 상태를 이어서 처리한다.

### 면접에서 말할 수 있게 정리

- **30초 버전**
  서버 점검 기록에서 응답 시간이 기준 이상인 서버만 generator로 생성하는 코드를 작성했는데 오류가 났다. `for`문으로 이미 꺼낸 딕셔너리에 `next()`를 다시 썼고, 서버 이름은 고정값으로 출력했고, 조건식은 기준값 자체만 검사하고 있었다. 반복 변수에 실제로 무엇이 들어오는지 다시 확인해서 세 곳을 모두 현재 요소 기준으로 고쳤고, 응답 시간이 300ms 이상인 결제 서버와 로그 서버만 생성되는 것을 확인했다.

  처음부터 독립적으로 완성하지는 못했다. 오류 원인과 수정 방향을 확인한 뒤 정상 실행까지 완료했다.

- **"다음에는 어떻게 하나요?"**
  `for 변수 in iterable`을 작성한 직후 반복 변수에 실제로 어떤 자료형과 값이 들어오는지 먼저 확인하고, 조건식의 왼쪽에는 현재 데이터가, 오른쪽에는 비교 기준이 들어갔는지 점검한다.
