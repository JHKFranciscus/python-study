## 2026-07-08 조건식 오류 수정

### 상황
시험 점수와 출석률을 각각 정수로 입력받고
int(), input(), if ,elif ,else ,and ,or을 사용하여
점수 또는 출석률이 0 미만이거나 100 초과이면
잘못된 입력입니다.
점수가 70 이상이고 출석률이 80 이상이면
수료입니다.
그 외에는
미수료입니다.
위 조건을 만족하는 수료 판정 프로그램을 작성했다.

### 문제
점수 105, 출석률 90을 입력했을 때
잘못된 입력이 아니라 수료라고 출력됐다.

### 내가 처음 시도한 방법
두 변수의 범위를 한꺼번에 검사하려고 (score or check_rate) < 0 and (score or check_rate) > 100을 사용했다.

### 잘못된 이유
`score or check_rate`는 두 변수를 모두 검사하는 표현이 아니었다.
두 값 중 참으로 취급되는 한 값을 반환하므로, 각 변수의 범위를 따로 비교하지 못했다.

또한 하나의 값이 동시에 0보다 작고 100보다 클 수 없으므로
`값 < 0 and 값 > 100` 조건은 항상 거짓이었다.

### 수정한 방법
score와 check_rate를 각각 비교하도록 조건식을 score < 0 or score > 100 or check_rate < 0 or check_rate > 100으로 수정함.
점수 85·출석률 105, 점수 85·출석률 -1을 입력해 다시 확인함.

### 결과
점수 85·출석률 105와 점수 85·출석률 -1을 입력했을 때
모두 `잘못된 입력입니다.`가 출력되는 것을 확인했다.
정상 범위의 입력에서는 수료와 미수료도 기준에 맞게 출력됐다.

### 이 경험에서 배운 점
여러 변수의 범위를 검사할 때는 변수마다 비교식을 따로 작성해야 한다.
코드가 실행된다는 것만으로 맞다고 판단하지 말고,
105, -1 같은 잘못된 입력과 경계값을 직접 넣어 확인해야 한다.

## 2026-07-11 - 통계 변수의 초기화 위치를 수정한 경험

### 1. 상황

### 3. 행동

scores와 total이 각각 언제까지 값을 유지해야 하는지 비교했다.

```python
def get_book_by_index(books, index):
    return books[index]
```

- 관리 클래스가 직접 가격을 바꾸는 것이 아니라, 검색한 상품 객체의 `change_price()`를 호출해야 한다는 것을 다시 확인했다.

### 수정한 방법
```python
def change_product_price(self, target_name, new_price):
    change_product = self.find_product(target_name)
    if change_product is not None:
        return change_product.change_price(new_price)
    return False
```

검색 실패 여부는 `None`으로 확인하고, 가격 변경 작업의 성공 여부는 `True`와 `False`로 반환하도록 역할을 나눴다.

### 실제 결과
존재하지 않는 상품의 가격 변경을 시도했을 때 오류가 발생하지 않고 `False`가 반환됐다. 기존 상품의 가격도 바뀌지 않았다.

### 배운 점
같은 '실패'처럼 보여도 메서드의 역할에 따라 반환값의 의미가 다르다. 객체 검색 실패에는 `None`, 변경이나 삭제 같은 작업 실패에는 `False`를 사용한다. 그리고 호출하는 쪽에서는 그 메서드의 반환 규칙에 맞춰 조건을 작성해야 한다.

결과적으로 `load_from_file()`은 파일 읽기와 등록만, 분리한 함수는 상품 종류 판단과 객체 생성만 담당하게 됐습니다.

## 2026-08-04 경험 후보 - 서버 점검 generator에서 반복 대상과 조건 판단 오류를 수정한 경험

### 한 줄 요약

서버 점검 기록을 generator로 처리하다 오류가 났는데, 정리해 보니 세 건의 원인이 하나였다. 서버 점검 기록을 generator로 처리하는 독립 재현에서 반복 변수 `check`를 현재 서버 기록이 아니라 iterator처럼 잘못 다뤘고, 출력과 조건식에서도 현재 요소 대신 고정값과 기준값을 사용해 오류가 발생했다.
### 상황

- iterable, iterator, generator의 기본 동작을 학습한 뒤 서버 점검 기록을 새로운 문제로 적용했다.
- iterator로 점검 기록을 한 건씩 처리하고, generator로 응답 시간이 기준 이상인 서버만 생성해야 했다.

### 문제

처음 작성한 generator 코드에서 오류가 발생했다.

**단순 오타 (1건)**

- `yield`를 `yeild`로 잘못 작성해 `SyntaxError`가 발생했다.

**반복 대상과 조건 판단 오류 (3건)**

- `for check in checks`로 이미 딕셔너리 한 건을 꺼냈는데 다시 `next(check)`를 호출했다. → `check`를 iterator로 봤다.
- 현재 서버 이름 대신 `"인증 서버"`를 고정 출력했다. → 현재 요소 대신 고정값을 썼다.
- `check["response_time"]`과 `standard`를 비교해야 했는데 `standard >= 300`으로 작성했다. → 현재 데이터 대신 기준값만 검사했다.

### 확인 과정

1. 오류가 발생한 줄을 확인했다.
2. 반복문 안의 `check`에 실제로 어떤 값이 들어오는지 다시 확인했다. `check`는 iterator가 아니라 이미 꺼낸 서버 기록 딕셔너리였다.
3. 조건식이 현재 기록의 응답 시간을 검사하지 않고 기준값 자체만 검사하고 있다는 점을 구분했다.

### 수정

- `yeild` → `yield`
- `next(check)` → 제거
- `"인증 서버"` 고정 출력 → `check["server"]`
- `standard >= 300` → `check["response_time"] >= standard`

### 결과

- 응답 시간이 300ms 이상인 결제 서버와 로그 서버만 생성됐다.
- 첫 번째 느린 서버는 `next()`로 처리하고, 남은 느린 서버는 같은 generator를 `for`문으로 이어서 처리했다.
- 다만 처음부터 독립적으로 완성한 것은 아니다. 오류 원인과 수정 방향을 확인한 뒤 정상 실행까지 완료했다.

### 배운 기준

- 세 오류는 모두 반복 변수 `check`의 역할을 정확히 사용하지 못한 데서 나왔다. `check`는 이미 현재 서버 기록 딕셔너리인데 iterator처럼 다뤘고, 출력과 조건식에서는 현재 요소 대신 고정값과 기준값만 사용했다.
- `for 변수 in iterable`에서 변수에는 이미 현재 요소가 들어온다. 그 변수에 다시 `next()`를 쓰지 않는다.
- 조건식에는 기준값뿐 아니라 실제로 검사하려는 현재 데이터가 포함되어야 한다.
- generator는 같은 객체를 계속 사용하면 이전 `yield`의 실행 상태를 이어서 처리한다.

### 면접에서 말할 수 있게 정리

- **30초 버전**
  서버 점검 기록에서 응답 시간이 기준 이상인 서버만 generator로 생성하는 코드를 작성했는데 오류가 났다. `for`문으로 이미 꺼낸 딕셔너리에 `next()`를 다시 썼고, 서버 이름은 고정값으로 출력했고, 조건식은 기준값 자체만 검사하고 있었다. 반복 변수에 실제로 무엇이 들어오는지 다시 확인해서 세 곳을 모두 현재 요소 기준으로 고쳤고, 응답 시간이 300ms 이상인 결제 서버와 로그 서버만 생성되는 것을 확인했다.

  처음부터 독립적으로 완성하지는 못했다. 오류 원인과 수정 방향을 확인한 뒤 정상 실행까지 완료했다.

- **"다음에는 어떻게 하나요?"**
  `for 변수 in iterable`을 작성한 직후 반복 변수에 실제로 어떤 자료형과 값이 들어오는지 먼저 확인하고, 조건식의 왼쪽에는 현재 데이터가, 오른쪽에는 비교 기준이 들어갔는지 점검한다.


## 2026-08-05 경험 후보 - 출력 결과와 구현 요구사항을 분리해 검증한 경험

### 한 줄 요약

출력은 맞았지만 요구사항대로 구현되지 않은 코드를 발견하고, 요구사항과 코드를 직접 대조하는 검증 순서를 만든 경험이다.

### 상황

함수 객체와 `filter()`, `map()`을 학습한 뒤 점수 처리 프로그램을 독립 재현했다. 이 경험과 직접 관련된 핵심 요구사항은 다음 두 가지였다.

- 선택한 보너스 함수 객체를 변수에 저장할 것
- 60점 이상인 학생만 골라 해당 함수를 적용할 것

### 문제

처음 작성한 프로그램은 예상한 결과를 그대로 출력했다.

```python
mapped = map(
    lambda student: apply_bonus(
        student,
        select_bonus("2"),
    ),
    filtered_scores,
)
```

그러나 완료 조건과 코드를 다시 대조하자, 선택한 함수 객체를 변수에 저장하지 않고 `map()` 내부에서 `select_bonus("2")`를 반복 호출하고 있었다. 출력값은 맞았지만 다음 요구사항은 충족하지 못한 상태였다.

```
함수 객체 선택 → 변수에 저장 → 저장한 함수 객체를 map에 전달
```

### 원인

프로그램의 최종 출력만 확인하고, 각 요구사항이 코드의 어느 부분에서 구현됐는지는 따로 확인하지 않았다. 그 결과 함수 선택과 함수 적용을 분리해야 한다는 구조적 조건을 놓쳤다.

### 수정

선택한 함수 객체를 먼저 변수에 저장한 뒤, 그 변수를 `map()`에 전달하도록 수정했다.

```python
selected_bonus = select_bonus("2")

mapped = map(
    lambda student: apply_bonus(student, selected_bonus),
    filtered_scores,
)
```

수정 후에는 다음 조건을 코드와 실행 결과로 하나씩 다시 확인했다.

- `selected_bonus`에 함수 객체가 저장됐는가
- `filter()`가 60점 이상만 통과시켰는가
- `map()`이 통과한 학생만 변환했는가
- 원본 점수 목록이 유지됐는가
- 소진된 `map` 객체의 재사용 결과가 `[]`인가

### 결과

수정 후에도 결과는 그대로 출력됐다.

```
지수 80 → 90
현우 67 → 77
서연 92 → 100
```

원본 점수 목록은 변경되지 않았고, 소진된 `map` 객체는 `[]`가 됐다. 최종적으로 출력 결과와 구현 요구사항을 모두 충족했다.

### 배운 점

프로그램의 결과가 맞는 것과 요구사항에 맞는 구조로 구현한 것은 별개의 문제다. 함수의 저장 위치, 역할 분리, 원본 보존처럼 실행 결과만으로 확인할 수 없는 조건은 요구사항과 코드를 직접 대조해야 한다.

앞으로는 다음 순서로 검증한다.

1. 실행 결과 확인
2. 요구사항별 구현 위치 확인
3. 원본 데이터와 객체 상태 확인
4. 완료 조건 최종 대조

### 활용 가능 범위

- 결과는 맞았지만 구현상의 누락을 발견한 경험
- 요구사항을 기준으로 코드를 다시 검증한 경험
- 자신의 검증 방식을 개선한 경험


## 2026-08-06 경험 후보 - 데코레이터의 입력 시점을 구분해 주문 처리 코드를 재구현한 경험

## 상황

클로저와 데코레이터를 학습한 뒤, 검사·로그·주문 계산·성공 횟수 누적 기능을 결합한 주문 처리 프로그램의 독립 재현을 시도했다.


**2) 처리와 기록의 역할이 섞였다**

성공 횟수를 기록하는 함수 안에서 주문 처리 함수를 다시 호출하려 하여, 처리와 기록의 역할도 섞였다.

## 행동

1차 독립 재현에서는 오류를 스스로 해결하지 못했다.
설명을 받은 뒤 다음과 같이 구조를 다시 나누었다.

- 데코레이터 바깥 함수는 원래 함수 객체를 받도록 수정했다.

- 주문 계산 함수는 주문을 처리하고, 성공 횟수 클로저는 처리 결과만 기록하도록 역할을 분리했다.
- 정상 주문과 실패 주문을 차례로 실행하여 반환값과 누적 횟수를 확인했다.

## 결과

보조 설명 후 프로그램을 재구현하여 다음을 확인했다.

- 정상 주문은 계산되고 성공 횟수가 증가했다.

- 원본 주문 딕셔너리는 변경되지 않았다.

책, 키보드, 마우스 주문을 차례로 처리하여 성공 횟수가 1 → 1 → 2로 누적되는 것을 확인했다.

수행 결과는 다음과 같다.

- 1차 독립 재현: 실패
- 보조 설명 후 재구현: 성공
- 최종 프로그램 실행: 성공

## 2026-08-07 경험 후보 - 예제에 맞춘 구현을 요구사항 기준으로 고친 경험

### 한 줄 요약
예제 출력만 보고 짠 코드가 실행 결과는 맞았지만 요구사항은 만족하지 못한다는 것을 발견하고, 입력 조건을 기준으로 동작하도록 고친 경험이다.

### 상황
파이썬 특수 메서드를 학습한 뒤 `NumberSequence` 클래스의 독립 재현을 시도했다.
`start`, `final`, `step`만 저장하고 별도의 값 목록은 만들지 않은 채, 반복과 길이 계산이 모두 가능해야 한다는 조건이었다.

### 문제
처음에는 예제 결과가 `2, 4, 6, 8, 10`인 것을 보고 `__iter__()`에 짝수만 통과시키는 조건을 넣었다.
실행 결과는 맞았지만, 요구사항에는 없는 규칙을 예제만 보고 추가한 구현이었다.
`__len__()`에서도 값을 모두 `list`로 만든 뒤 길이를 구해, 값을 미리 만들지 않는다는 조건을 만족하지 못했다.

### 수정
예제의 숫자가 아니라 `start`, `final`, `step`이 실제 규칙이라는 점을 다시 확인했다.
짝수 조건을 제거하고 `range`에서 `step`에 따라 값을 생성하도록 수정했다.
이후 `range` 자체가 iterable이므로 `iter(range(...))`를 바로 반환할 수도 있다는 더 간단한 방식을 확인했다.
길이는 먼저 `start`, `final`, `step`만으로 직접 계산하도록 고쳤고, 이후 `len(range(...))`으로 같은 결과를 더 간단하게 얻을 수 있다는 것을 확인해 그 방식으로 정리했다. 불필요한 `list` 생성도 함께 없앴다.

### 결과
예제에만 맞는 코드에서 벗어나 입력 조건을 기준으로 동작하는 코드로 수정했다.
또한 이미 반복과 길이 계산에 필요한 기능을 제공하는 `range`를 다른 자료구조로 변환하지 않고 그대로 사용할 수 있게 되었다.

### 배운 점
예제 출력이 맞는 것과 요구사항을 올바르게 구현한 것은 다르다.
두 실수 모두 결과가 예제와 같은지에만 집중하다 생긴 것이었다.
구현 전에 예제에서 우연히 보이는 패턴과, 입력이 달라져도 유지되어야 하는 실제 규칙을 구분해야 한다는 기준을 얻었다.

### 예상 꼬리 질문
- **왜 짝수 조건을 넣었나?** → 예제 출력이 `2, 4, 6, 8, 10`이어서 그 숫자만 보고 규칙을 판단했다고 답한다.
- **잘못된 것을 어떻게 알았나?** → 구현 결과를 확인받는 과정에서, 짝수 조건은 요구사항에 없는 조건이고 `list()` 생성 역시 값을 미리 만들지 않는다는 조건에 어긋난다는 피드백을 받아 확인했다.
- **지금이라면 어떻게 접근하겠나?** → 예제부터 코드로 옮기지 않고, 요구사항에 적힌 조건을 먼저 구현한 뒤 예제로 검증하겠다고 답한다.

### 활용 포인트
- 결과만 맞는 코드의 문제를 발견하고 요구사항 기준으로 수정한 경험
- 예제에 과적합된 조건을 제거하고 일반화한 경험
- 불필요한 중간 자료구조 생성을 줄인 경험

- **decorator 해석** — `@decorator(x)`를 `decorator(x)(원래 함수)`로 풀어, 각 단계에 무엇이 전달되는지 확인했다.
- **decorator 구현** — 검사 함수, 원래 함수, 실제 호출값이 각각 다른 단계에서 전달된다는 점을 기준으로 수정했다.

---

**독립적으로 수행한 것**

- collection/요소 구분, 변수 추적, `func`/`func()` 판단, 함수 인수 역추적

**안내를 받고 수정한 것**

- 인수 있는 decorator 직접 구성
  → 첫 시도에 실패했고, 안내를 받은 뒤 수정했다.

**독립 성공으로 처리하지 않은 것**

- 최종 통합 독립 재현
  → 외부 AI 도움을 받아 완성했으므로 독립 성공으로 처리하지 않았다.

- **프로필 박스화**: `input`에 `border`를 주는 것이 아니라, 프로필 영역 전체를 감싸는 요소를 꾸며야 했다.

property부터 작성하지 않고, 적용할 위치를 먼저 정하는 기준을 세웠다.

> **꾸밀 대상 확인 → 배치할 요소 확인 → 배치 요소들의 직접 부모 확인**

이 페이지에서 Flexbox를 적용한 위치는 네 곳이고, **네 곳 모두 배치할 요소의 직접 부모**다.

| box 2개 | 두 box를 감싼 `<section>` | 가운데 배치 (`justify-content-center`) |

## 배운 점

## 2026-08-16 경험 후보 —  CSS 적용 위치 혼동을 판단 기준으로 바꾼 경험

### 한 줄 요약

CSS 문법은 알고 있었지만 **"어느 요소에 적용할지"** 에서 반복해서 막혔고, 브라우저로 직접 비교해 판단 기준을 만든 뒤 다음 구현에 적용했다.

---

### 상황

HTML/CSS와 Flexbox를 학습한 뒤 직접 페이지를 구현했다. 그런데 CSS property의 의미를 알고 있어도, **어느 HTML 요소에 적용해야 하는지** 판단하는 과정에서 반복해서 막혔다.

### 문제

- 카드 여러 개를 배치하면서 `.card` 자체에 `display: flex`를 적용하려 했다.
- 버튼 자체가 변해야 하는 상황에서 부모 요소를 selector로 선택했다.

문법을 모르는 문제라기보다, **요구사항과 HTML 구조를 연결하는 판단**이 부족한 문제라고 판단했다.

### 행동

- 화면에서 구조가 명확하지 않을 때는 요소에 임시로 `border`를 적용해 실제 영역을 확인했다.
- 부모와 자식에 `display: flex`를 번갈아 적용·제거하면서 브라우저 결과를 비교했다.
- 비교한 결과를 다음 기준으로 정리했다.
  - 여러 요소를 **배치**한다 → 그 요소들의 **직접 부모**를 찾는다.
  - 특정 요소 **자체가 변한다** → 그 **요소 자체**를 선택한다.
- 이후에는 CSS를 바로 작성하지 않고, 아래 순서로 먼저 판단했다.

```
요구사항 → 대상 → HTML 구조 → selector → CSS
```

### 결과

- **6일차**: 이전 페이지와 구조가 다른 페이지를 완성 코드 없이 독립 구현하는 데 성공했다.
- **일요일 종합 구현**: 일부 적용 대상 판단 오류가 다시 발생했지만, 문제점을 지적받은 뒤 정답 코드를 옮기지 않고 직접 수정했다.

판단 기준이 완전히 자동화된 단계는 아니다. 다만 반복되는 실수를 단순 암기로 넘기지 않고, **검증 가능한 기준**으로 바꾸어 다음 구현에 적용한 경험이다.

## 2026-08-17 경험 후보 — 개별 개념은 알지만 실행 흐름을 연결하지 못한 문제를 구현 단계로 나눠 좁힌 경험

### 상황

JavaScript 기본 문법과 DOM/event 조작을 학습한 뒤, 버튼을 클릭하면 조건을 판단해 화면의 문구를 변경하는 기능을 완성 코드 없이 구현했다.

---

### 문제

- **주 문제** — HTML 요소 찾기와 조건식 작성까지는 직접 했지만, 클릭 event와 실행할 함수를 연결하지 못했고 조건문을 어느 위치에 넣어야 하는지도 판단하지 못했다.

---

### 확인한 과정

작성한 코드를 처음부터 다시 고치기보다, 어느 단계까지 스스로 구현했는지 나누어 봤다.

- 요소 찾기 → 가능
- 상태값과 조건식 작성 → 가능
- **――― 여기서부터 막힘 ―――**
- event 등록 → 막힘
- event 발생 후 조건 판단과 DOM 변경 연결 → 막힘

경계선은 **event 등록 지점**이었다. 이를 통해 문제를 JavaScript 전체가 아니라 event 이후의 실행 흐름을 연결하는 부분으로 좁혔다.

---

### 보완한 방법

핵심 구조를 안내받은 뒤, `addEventListener()`가 event 발생 시 실행할 함수를 등록한다는 점을 다시 확인하고 조건 판단과 `textContent` 변경을 그 함수 안에 배치했다. 또한 `textContent`가 method가 아닌 property라는 점을 확인해 문자열을 대입하는 방식으로 수정했다.

---

- 최초 독립 재현에는 실패했다.
- 안내를 받은 뒤에는 코드 구조를 **요소 찾기 → event 등록 → 조건 판단 → DOM 변경** 순서로 다시 연결할 수 있었다.

---

### 얻은 기준

DOM 탐색 method를 먼저 고르지 않는다.
**"필요한 대상이 하나인가, 여러 개인가?"** 를 먼저 판단한 뒤 `querySelector()`와 `querySelectorAll()` 중에서 선택한다.

---

### 상황
- Ajax 학습 후 독립 재현에서 도서 조회 GET 기능과 구매 요청 POST 기능을 직접 구현했다.
- 코드만 작성해보는 단계였기 때문에 Live Server를 사용하고 있었다.
- POST는 `/orders`로 도서 번호와 수량을 전송하도록 작성했다.

---

### 문제
- 구매 요청을 실행하자 Console에 `POST /orders 405 (Method Not Allowed)`가 발생했다.
- success callback은 실행되지 않았다.

---

### 확인한 과정
- 화면 결과만으로 판단하지 않고, Console의 request 기록과 HTTP status code의 의미를 기준으로 실행 흐름을 다시 짚었다.
- 서버가 `405`라는 응답을 돌려주었다는 것은 request가 서버까지 도달했다는 뜻이라고 판단했다.
- 그래서 진행 지점을 **click handler → `$.ajax()` → POST request → 서버 도착**까지로 확인했고, 실패한 곳은 그 다음 단계인 서버의 POST method 처리라고 정리했다.
- 원인이 경로 때문인지 method 때문인지 구분하기 위해, 같은 Live Server에 조건을 하나씩 바꿔가며 request를 보내 결과를 비교했다.

| 보낸 request | 결과 |
| --- | --- |
| 없는 경로 + POST (`/orders`) | `405 Method Not Allowed` |
| 없는 경로 + GET | `404 Not Found` |
| 있는 경로 + POST | `405 Method Not Allowed` |

- 경로를 없는 상태로 고정하고 method만 바꾸자 `404`와 `405`로 결과가 갈렸고, method를 POST로 고정하고 경로만 바꾸자 결과가 `405`로 동일했다.
- 두 방향을 함께 보고, 이번 `405`의 원인은 경로가 아니라 POST method라는 것을 확인했다.

---

### 원인
- Live Server는 파일을 내려주는 용도의 정적 서버라, 경로가 있든 없든 POST request 자체를 처리하지 않는다. 그래서 `405 Method Not Allowed`가 돌아왔다.
- POST url로 지정한 `/orders`가 만들지 않은 경로였던 것은 맞지만, 위 비교를 통해 그것이 `405`의 원인은 아니라는 것을 확인했다.
- 즉 이번 오류는 Ajax 코드의 문제가 아니라, POST를 처리할 수 있는 서버가 없는 환경에서 요청을 보냈기 때문에 발생한 것이었다.

---

### 결과
- 이번 문제의 발생 지점이 Ajax 요청 이전이 아니라 서버의 method 처리 단계라는 것을 확인했다.
- JavaScript가 실행되지 않은 경우와, 실행은 되었지만 서버가 request를 처리하지 못한 경우를 구분할 수 있게 되었다.
- 작성한 Ajax 코드 자체는 서버까지 request를 보내는 데 문제가 없었다는 것도 함께 확인했다.

---

### 배운 점
- 오류가 발생했을 때 화면 결과만 보고 판단하지 않고, Console의 request와 HTTP status code를 이용해 **어디까지 정상 실행되었는지부터 좁혀가는 방식**으로 원인을 확인해야 한다는 기준을 얻었다.
- 원인이 두 가지로 의심될 때는 추측으로 두지 않고, **조건을 하나씩 고정하고 나머지 하나만 바꿔서** 다시 요청해보면 어느 쪽이 원인인지 구분할 수 있다.
- 오류의 원인이 항상 코드에 있는 것은 아니며, 지금의 실행 환경이 그 요청을 처리할 수 있는 환경인지도 함께 확인해야 한다.

## 경험 1 — 정상 동작하는 코드에서 비동기 실행 시점의 문제를 확인하고 수정한 경험

### 한 줄 요약

도서 조회 기능이 정상적으로 동작한 뒤에도 비동기 실행 순서를 다시 추적해, input 값을 읽는 시점에 따라 다른 값을 사용할 가능성을 확인하고 구조를 수정했다.

### 상황

주간 독립 재현에서 사용자가 입력한 도서 번호를 이용해 `books.json`을 조회하는 기능을 만들었다.

조회 버튼을 누르면 Ajax GET request를 보내고, response 배열에서 해당 도서 객체를 찾아 제목, 가격, 재고와 구매 상태를 화면에 출력하도록 구현했다.

도서 번호 `0`, `1`, `2`를 각각 입력했을 때 기능은 정상적으로 동작했다.

### 막혔던 점

처음 구현한 코드에서는 도서 번호를 다음처럼 `success` callback 안에서 읽었다.

```javascript
success: function(response) {
    const bookNumber = Number($("#bookNumber").val());
    // ...
}
```

당장 `0`, `1`, `2`를 조회했을 때는 문제가 없었기 때문에 기능만 보면 정상적으로 보였다.

하지만 비동기 실행 순서를 다시 확인하면서, `success` callback은 request 직후가 아니라 response가 도착한 뒤 실행된다는 점 때문에 input 값을 읽는 시점에 문제가 생길 수 있다는 것을 확인했다.

### 내가 한 것

일반 함수 실행과 Ajax의 비동기 실행 순서를 다시 비교했다.

Ajax에서는 다음과 같이 진행된다는 점을 코드에 대입해 확인했다.

```text
조회 버튼 클릭
→ request 전송
→ response를 기다리는 동안 사용자는 다른 동작을 할 수 있음
→ response 도착
→ success callback 실행
```

따라서 도서 번호를 `success` 안에서 읽으면 **조회 버튼을 눌렀을 때의 값이 아니라 response가 도착했을 때 input에 들어 있는 값**을 읽게 될 수 있다는 점을 확인했다.

이 문제 상황에서 input 값을 실제로 변경해 결과가 달라지는 것까지 브라우저에서 별도로 재현한 것은 아니다. 실행 순서를 코드에 대입해 문제 가능성을 확인한 뒤 구조를 수정했다.

### 어떻게 수정했나

도서 번호를 Ajax response가 도착한 뒤 읽지 않고, click callback이 실행될 때 먼저 읽어 변수에 저장하도록 바꿨다.

```javascript
$("#findBook").on("click", function () {
    const bookNumber = Number($("#bookNumber").val());

    $.ajax({
        url: "books.json",
        type: "GET",
        success: function (response) {
            const book = response[bookNumber];

            $("#title").text(book.title);
            $("#price").text(book.price);
            $("#stock").text(book.stock);

            if (book.stock > 0) {
                $("#order").text("구매 가능");
            } else {
                $("#order").text("품절");
            }
        }
    });
});
```

### 결과

이제 도서 번호는 조회 버튼을 누른 시점에 먼저 확정된다.

따라서 Ajax response가 돌아오기 전에 input 내용이 바뀌더라도, 해당 조회 작업에서는 클릭 당시 저장한 `bookNumber`를 사용하도록 구조가 바뀌었다.

### 배운 점

비동기 코드에서는 **어떤 값을 사용하는가뿐 아니라 그 값을 언제 읽고 확정하는가도 중요하다.**

또한 코드가 현재 입력에서 정상적으로 동작한다는 사실만으로 구현이 끝났다고 판단하지 않고, 실행 순서를 다시 추적해 볼 필요가 있다는 것을 확인했다.

### 면접에서 꺼낼 한 문장

> 도서 조회 기능은 정상적으로 동작했지만 비동기 실행 순서를 코드에 다시 대입해 보면서 input 값을 `success` 안에서 읽으면 클릭 이후의 값을 사용할 가능성이 있다는 점을 확인했고, 클릭 시점에 값을 먼저 저장하도록 구조를 수정했습니다.

> **이 경험의 핵심은 새로운 현상을 직접 발견했다는 것보다, 배운 비동기 실행 순서를 내 코드에 다시 적용해 구조를 검토하고 수정했다는 점이다.**

## 경험 2 — `405` 오류에서 요청이 어디까지 갔는지부터 확인한 경험

### 한 줄 요약

Ajax POST 요청에서 `405 Method Not Allowed`가 발생했을 때 Client 코드만 반복해서 수정하지 않고, HTTP status를 기준으로 요청이 어느 단계까지 진행됐는지 확인한 뒤 원인의 범위를 좁혔다.

### 상황

Ajax POST 연습에서 도서 번호와 주문 수량을 `data`에 담아 `/orders`로 보내는 코드를 작성했다.

```javascript
$.ajax({
    url: "/orders",
    type: "POST",
    data: {
        bookNumber: bookNumber,
        quantity: quantity
    },
    success: function (response) {
        // ...
    }
});
```

실행 결과:

```text
405 Method Not Allowed
```

가 발생했다.

### 막혔던 점

처음에는 다음 중 무엇이 문제인지 바로 판단하지 못했다.

1. 내가 작성한 Ajax 코드 자체가 잘못됐는가?
2. 요청 경로가 잘못됐는가?
3. POST method가 문제인가?
4. 현재 사용 중인 Server 환경이 요청을 처리하지 못하는가?

### 내가 직접 한 것

먼저 Console과 HTTP status를 확인했다.

`405`라는 HTTP response가 돌아오고 있다는 사실을 보고, 코드가 아예 실행되지 않는 상황이라기보다 **HTTP Server가 요청을 받고 method에 대한 판단을 한 뒤 response를 돌려주고 있는 상황**으로 판단했다.

그다음 경로와 HTTP method 조건을 바꾸어 다시 요청하면서 어떤 조건에서 결과가 달라지는지 확인했다.

즉 처음부터 Client 코드를 전부 고치기보다 다음 순서로 범위를 좁혔다.

```text
Ajax 코드 실행 여부 확인
→ HTTP response/status 확인
→ 요청이 Server까지 전달되는지 판단
→ 경로와 method 조건 변경
→ Server 환경 확인
```

### 최종 원인을 확인한 경로

여기서 **최종 환경 원인을 내가 혼자 찾아낸 것은 아니다.**

직접 status와 요청 조건을 확인하면서 문제 범위를 좁힌 뒤, ChatGPT에 코드와 상황을 검토받고 Claude의 요청에 따라 추가 실행도 해보면서 현재 사용 중인 Live Server의 역할을 확인했다.

그 결과 현재 Live Server는 정적 파일을 제공하는 용도의 Server이며, 내가 요청한 `POST /orders`를 처리할 Server 로직이 존재하지 않는다는 점을 확인했다.

따라서 Client의 Ajax 문법만 수정해서 해결할 수 있는 문제가 아니었다.

### 결과

`405`를 단순히 “POST가 실패했다”라고만 보지 않고,

> 요청은 어느 단계까지 정상적으로 진행됐는가?

를 먼저 판단할 수 있게 됐다.

또한 다음 status code도 Server가 request를 어떻게 판단했는지를 기준으로 구분했다.

* `200` : 요청을 정상적으로 처리함
* `404` : 요청한 resource를 찾지 못함
* `405` : 해당 resource에서 요청한 HTTP method를 허용하지 않음
* `500` : Server가 요청을 처리하는 과정에서 내부 오류가 발생함

### 배운 점

오류가 발생했을 때 보이는 코드부터 무작정 수정하는 것이 아니라,

```text
Client
→ 통신
→ Server
```

중 **어디까지 정상적으로 진행됐는지 먼저 확인한 뒤 문제 범위를 좁히는 방식**이 필요하다는 것을 배웠다.

또한 최종 원인을 AI 도구의 도움으로 확인했다면, 내가 직접 확인한 부분과 도움받은 부분을 구분해서 기록해야 한다.

### 면접에서 꺼낼 한 문장

> Ajax POST 요청에서 405가 발생했을 때 status code를 보고 Server가 요청에 응답하고 있다는 점부터 확인했습니다. 이후 경로와 method를 바꿔가며 범위를 좁혔고, 최종적으로는 AI 도구의 도움을 받아 사용 중인 Live Server가 정적 파일 제공용이라 `POST /orders`를 처리할 로직이 없다는 점을 확인했습니다.

> **이 경험의 핵심은 원인을 전부 혼자 찾아냈다는 것이 아니라, 오류가 난 지점부터 무작정 고치지 않고 요청이 어느 단계까지 정상인지 확인하며 문제 범위를 좁혔다는 점이다.**

## 두 경험을 같이 남기는 이유

두 경험은 비슷해 보이지만 보여주는 행동이 다르다.

### 경험 1

```text
기능 구현
→ 정상 동작
→ 실행 순서 재검토
→ 잠재적인 문제 확인
→ 구조 수정
```

배운 내용을 내 코드에 다시 적용해 **검증하고 개선한 과정**이다.

### 경험 2

```text
오류 발생
→ HTTP response 확인
→ 요청 도달 범위 판단
→ 조건 변경
→ 문제 범위 축소
→ 환경 원인 확인
```

문제가 발생했을 때 **원인의 범위를 단계적으로 좁힌 과정**이다.

따라서 두 경험은 겹치지 않으므로 모두 경험은행에 남긴다.

## 2026-08-24 경험 후보 — Flask routing 구현 실패에서 request 흐름을 단계로 나눠 원인을 좁힌 경험

**한 줄 요약**
Flask를 처음 배운 날 routing 구현에 두 번 모두 실패했지만, 코드를 통째로 고치는 대신 request의 흐름을 단계로 나눠 어디까지 정상적으로 갔는지 확인하며 원인을 좁혔고, 결과가 나왔다는 이유만으로 "완료"로 기록하지는 않았다.

---

### 상황

Flask를 처음 학습한 날이었다. 정적 route와 동적 route, GET/POST를 배운 뒤 직접 routing을 구현하고 독립 재현까지 진행했다.

설명을 들을 때는 각 개념을 따라갈 수 있었지만, 처음부터 여러 route와 form 요청을 직접 연결하려고 하자 두 번 모두 최초 구현에 실패했다.

---

### 문제

1. **첫 번째 구현** — 동적 route 문법, 함수 이름, `Flask(__name__)` 등을 제대로 연결하지 못했다.
2. **두 번째 재현** — 코드를 수정했는데도 form의 POST 요청이 원하는 결과로 이어지지 않았다. 특히 Live Server는 5500번 port, Flask는 5000번 port에서 실행되고 있었기 때문에, 코드만 보고서는 어느 단계에서 문제가 발생했는지 바로 판단하기 어려웠다.

---

### 내가 한 것

오류가 날 때마다 전체 코드를 한꺼번에 바꾸기보다, request의 흐름을 단계로 나눠서 어디까지 정상적으로 진행됐는지 확인했다.

```
어느 path로 요청했는가
→ GET인가 POST인가
→ 어느 port로 갔는가
→ 그 요청과 맞는 route가 있는가
→ 어떤 함수가 호출되는가
```

각 단계를 실제 실행 결과와 비교했다.

- `/members`와 `/members/12`의 차이
- 주소창의 GET과 form의 POST 차이
- `localhost:5500`과 `127.0.0.1:5000`의 차이

안내가 필요한 부분은 수정한 뒤, 다시 직접 실행해서 조건별 결과를 확인했다.

---

### 결과

필요한 동작은 모두 확인했다. (전체 결과는 부록 1)

다만 수정 과정에서 안내받은 코드를 그대로 사용한 부분이 있었기 때문에, **최종 코드가 동작했다는 이유만으로 독립 구현에 성공했다고 기록하지는 않았다.** 두 번의 구현 모두 `최초 시도 실패 → 안내 후 보완 완료`로 판단했다.

---

### 배운 점

**1. 원인을 좁힐 때는 코드가 아니라 흐름을 나눈다**
처음 접하는 기술에서 오류가 나면 코드 전체를 막연히 보게 되는데, 그것보다 request와 실행 흐름을 단계별로 나누어 어느 단계까지 정상적으로 진행됐는지 확인하는 편이 원인을 좁히는 데 도움이 됐다.

**2. "동작했다"와 "설명하고 다시 만들 수 있다"는 다른 기준이다**
앞으로는 `실행 결과가 맞다`와 `내가 원리를 설명하고 다시 구현할 수 있다`를 별도의 학습 완료 기준으로 두고 확인하기로 했다. 이번 경험을 `성공`이 아니라 `보완 완료`로 기록한 것이 그 기준을 실제로 적용해본 첫 사례다.

**3. 서버가 둘 이상 실행될 때는 request가 어느 port로 향하는지 먼저 확인한다.**
이번에는 Live Server와 Flask가 서로 다른 port에서 실행되고 있었고, request가 의도한 서버가 아닌 곳으로 가는 문제가 있었다. 이후 여러 서버가 동시에 실행되는 환경에서는 path와 method뿐 아니라 request의 목적지 port도 먼저 확인하기로 했다.

## 2026-08-25 경험 후보 — HTML form과 Flask의 연결을 HTTP request 흐름으로 이해한 경험

**한 문장 요약 (면접용)**
form 문법은 따라 쓸 수 있었지만 전체 흐름을 스스로 설명하지 못해서, GET form과 POST form을 각각 직접 실행해 비교하면서 브라우저가 만드는 request가 서버 코드의 어디로 연결되는지 정리한 경험이다.

**외워둘 흐름 3줄**

- `action` → request path → Flask route → 함수
- `input name` → 전송 데이터 → `request.args` / `request.form`
- Python 값 → `render_template()` → Jinja → 결과 HTML

---

### 상황

Flask에서 HTML form 입력값을 처리하는 내용을 학습했다. 코드의 각 문법은 예제를 보고 따라 작성할 수 있었지만, form과 Flask 코드가 어디서 어떻게 이어지는지는 잡히지 않은 상태였다.

### 문제 — 헷갈렸던 것 3가지

**(1)** `action="/search"`가 Python 함수를 직접 실행한다고 생각했다.

**(2)** URL이 바뀌면 서버도 바뀌는 것인지 혼동했다.

**(3)** GET과 POST에서 입력값이 어디로 전달되는지 정확히 구분하지 못했다.

정리하면 `form → HTTP request → Flask route → 함수 → 입력값 처리 → template`이라는 전체 연결을 스스로 설명하거나 구성하지 못했다.

### 행동 (문제와 같은 번호)

**(1)** form을 직접 제출해 보면서, `action="/search"`는 브라우저가 `/search`로 새 HTTP request를 보내는 것이고 그 request가 Flask routing을 거쳐 함수와 연결된다는 순서를 확인했다.

**(2)** 주소가 바뀔 때마다 host와 port를 확인했다. `127.0.0.1:5000`이 그대로면 같은 Flask 서버이고 path와 query string만 달라진 것이라고 정리했다.

**(3)** GET form을 실행해 입력값이 query string에 붙는 것을 주소창에서 확인하고 `request.args`로 값을 꺼냈다. 같은 예제를 POST로 변경해, 주소창에는 값이 보이지 않아도 request body의 form 데이터를 `request.form`으로 받을 수 있다는 차이를 확인했다.

**(마무리) 직접 구성한 것**
같은 `/profile` path에서 GET과 POST를 모두 허용하고 `request.method`에 따라 입력 화면과 결과 처리를 나눴다. 마지막에는 GET 검색과 POST 문의 기능을 하나의 Flask 애플리케이션 안에서 직접 구성했다. 최초 실행은 route 함수 이름 중복 오류로 실패했고, 원인을 확인한 뒤 함수 이름을 분리해서 정상 실행했다.

### 결과

- GET에서는 query string과 `request.args`, POST form에서는 request body와 `request.form`을 구분해서 직접 구현했다.
- 같은 path에서 `request.method`로 동작을 나누는 것까지 만들었다.
- 이제 form과 Flask 코드를 볼 때 위의 흐름 3줄을 기준으로 추적할 수 있다.

**정직하게 남길 부분**
마지막 독립 재현에서 난 함수 이름 중복 오류는 원인을 스스로 찾은 것이 아니라 안내를 받은 뒤 알았다. 오류 상황을 확인하고 함수 이름을 분리해 다시 실행해서 정상 동작을 확인한 것은 직접 했다.

### 배운 점

웹 코드는 문법을 개별적으로 외우기보다, 브라우저가 어떤 request를 만들고 그 request의 값이 서버 코드의 어디로 전달되는지 추적하는 것이 중요하다는 것을 배웠다. 실제로 헷갈렸던 3가지도 GET form과 POST form을 각각 실행해서 눈으로 비교하니 정리됐다.

### 보완할 점

- 여러 route와 template이 동시에 등장하면 연결 관계를 빠르게 판단하는 속도가 아직 느리다.
- route를 추가할 때 함수 이름까지 스스로 점검하는 습관이 아직 필요하다.

### B. 예상 꼬리 질문과 답변 방향

**Q. form을 제출하면 실제로 무슨 일이 일어나나?**
브라우저가 `action`의 path로 새 HTTP request를 만들어 보내고, Flask가 routing으로 그 path에 연결된 함수를 실행한다고 답한다. Python 함수를 직접 부르는 게 아니라는 점을 강조한다.

**Q. GET과 POST는 언제 어떤 걸 쓰나?**
직접 만들어 본 범위에서는 검색처럼 조회하는 것은 GET, 문의 등록처럼 값을 보내는 것은 POST로 했다고 답한다. GET은 값이 URL query string에 남고 POST는 body로 간다는 차이를 기준으로 설명한다.

**Q. `request.args`와 `request.form`의 차이는?**
`request.args`는 URL query string에서, `request.form`은 request body의 form 데이터에서 값을 꺼낸다고 답한다.

**Q. POST를 쓰면 데이터가 안전한가?**
주소창에 보이지 않을 뿐이고 데이터를 암호화하는 방식은 아니라고 답한다.

**Q. 같은 path에서 GET과 POST를 어떻게 나눴나?**
`/profile` 하나에 GET과 POST를 모두 허용하고 `request.method`로 분기해서, GET이면 입력 화면을 보여주고 POST면 form 값을 처리하도록 만들었다고 답한다.

**Q. 함수 이름 중복 오류는 어떻게 알았나?**
원인 자체는 안내를 받고 알았다고 솔직히 말한다. 대신 오류가 난 상황을 확인하고 함수 이름을 분리한 뒤 다시 실행해서 정상 동작을 확인한 것은 직접 했다고 덧붙이고, 그 뒤로는 route를 추가할 때 함수 이름부터 본다고 말한다.

**Q. 이 경험에서 무엇을 얻었나?**
문법을 따로 외우는 방식에서, 브라우저가 만든 request를 서버 코드까지 따라가며 보는 방식으로 바꾼 것이 가장 큰 변화라고 답한다.

- 한 개의 데이터 = list 안의 dictionary
- 식별값 = 각 dictionary 안의 `id`
- 대상 찾는 법 = 반복문으로 돌면서 `id` 비교

**이번 구조 — `dictionary 안의 dictionary`**

- 전체 = `tasks` dictionary
- 한 개의 데이터 = `tasks` 안의 dictionary
- 식별값 = 바깥 dictionary의 key (`python`, `flask`, `http`)
- 대상 찾는 법 = key로 바로 접근, 반복문 불필요

> **한 문장으로**: 식별값이 안쪽에 있느냐(`id`), 바깥 key 자체냐에 따라 "찾는 코드"가 있어야 하는지 없어도 되는지가 갈린다.

---

### 3. 예상 꼬리질문과 답변 방향

**Q. 안내를 받았다고 하셨는데, 정확히 어느 부분이었나요?**
→ dictionary 안의 dictionary 접근 방법, 그리고 동적 route 연결이다. 이 두 군데를 정확히 말하고, 나머지 부분도 완전히 혼자 한 건 아니라는 점을 굳이 숨기지 않는다.

**Q. 그럼 지금 다시 하면 혼자 하실 수 있나요?**
→ 구조는 이해했지만, 안내 없이 처음부터 재현해본 건 아직 확인하지 못했다고 그대로 말한다. 그리고 "다음에 할 것" 1번으로 연결한다. 여기서 할 수 있다고 말해버리면 검증이 안 된다.

**Q. 왜 처음에 반복문으로 찾으려고 하셨나요?**
→ 이전 구현이 별도 `id` 기반이었고, 기능 이름이 같으니 이전 코드 구조를 그대로 가져오려 했기 때문이다. 이게 이 경험의 핵심 실수 지점이고, 배운 점이 여기서 나온다.

**Q. 두 구조 중 어느 쪽이 더 나은가요?**
→ 아직 정리하지 못한 부분이다. 이번 경험에서 확인한 범위(식별값이 어디에 있느냐가 다르다)까지만 말하고, 장단점 비교는 모른다고 한다.

## 2026-08-28 경험 후보 — Ajax 기능에서 서버 문제와 화면 문제를 분리해 확인한 경험

> **한 줄 요약**
> 즐겨찾기 토글이 한 방향만 동작하지 않았을 때, 코드를 고치기 전에 `response`를 Console에 출력해서 서버 문제인지 JavaScript 문제인지부터 나눴고, 범위를 DOM 변경 쪽으로 좁혔다.

> **관련 기록**: 8주차 5일차 공부일지 (같은 날 같은 기능) — 직접/안내 구분은 두 문서가 일치한다
> **키워드**: Flask, jQuery Ajax, JSON response, DOM, 문제 범위 좁히기

---

### 상황

Flask + jQuery Ajax로 책의 즐겨찾기 상태를 반전시키고, JSON response를 받아 **해당 책의 화면만** 갱신하는 기능을 구현했다.

그런데 한 방향만 동작했다.

- `즐겨찾기 아님 → 즐겨찾기` : **동작함**
- `즐겨찾기 → 즐겨찾기 아님` : **화면이 안 바뀜**

---

### 문제 — 원인 후보가 세 개였다

어디가 문제인지 바로 구분할 수 없었다.

1. Flask의 **상태 변경**이 실패한 것인지
2. **response** 자체가 잘못된 것인지
3. JavaScript의 **DOM 변경**이 실패한 것인지

---

### 내가 한 행동 / 결과

> 번호는 위 「문제」의 후보 번호와 1:1로 이어진다.

**먼저 한 것 — 무작정 코드를 수정하지 않았다.**
Ajax `success`에서 `response`를 Console에 출력했다. 확인 결과 서버에서는 `favorite` 값이 `true / false`로 정상적으로 반전되고 있었다.

이 확인 하나로 후보 세 개 중 두 개가 정리됐다.

1. **배제** — 서버의 상태 변경은 정상이었다.
2. **배제** — JSON response도 정상이었다.
3. **남음** — 문제 범위를 `JavaScript → DOM 변경` 쪽으로 좁혔다.

**그 다음**
이후 안내를 받아, `false`일 때 사용하는 class selector에서 `.`이 빠진 것을 확인하고 수정했다.

---

### 결과

수정 후 두 방향 모두 정상 동작하는 것을 **실제 실행으로** 확인했다.

- `즐겨찾기 아님 → 즐겨찾기`
- `즐겨찾기 → 즐겨찾기 아님`

---

### 배운 점

서버와 JavaScript가 연결된 기능에서 문제가 생기면, 전체 코드를 한꺼번에 의심하기보다

```
request → 서버 처리 → response → JavaScript → DOM
```

이 순서로 **어디까지 정상인지**를 확인하면 문제 범위를 줄일 수 있다.

`response`를 확인하는 건 한 번의 확인으로 서버 쪽 후보를 한꺼번에 정리할 수 있는 지점이었다.

---

### 혼자 한 것 / 안내받은 것

**직접 한 것**
- 코드를 고치기 전에 Console의 `response`를 확인해, 서버 상태 변경과 JSON response가 정상임을 확인한 것
- 문제 범위를 JavaScript / DOM 쪽으로 좁힌 것
- `list 안의 dictionary`에서 id를 비교해 대상을 찾는 구조를 구현한 것

**안내받은 것**
- class selector의 `.` 누락 **위치** 확인
- `templates` / `static` 구성과 `render_template()`, `url_for("static", filename=...)`을 이용해 HTML·JavaScript·Flask를 연결해 실행하는 방법
- 초기 HTML 상태와 서버 메모리 상태 불일치 원인 설명

**정리**
문제 범위를 좁히는 데까지는 직접 했지만, **정확한 오타 위치를 찾은 건 안내를 받은 것**이다. 이 둘을 구분해서 말해야 한다.
반대로 **범위를 서버 / JavaScript로 나눠 좁힌 판단은 안내 없이 한 것**이다. 이 경험에서 면접에 쓸 부분은 사실상 그거라서, 이건 축소하지 않고 그대로 말한다.

## 부록

### A. 30초 면접 스크립트

> Flask와 jQuery Ajax로 즐겨찾기 토글 기능을 만들었는데, 켜는 건 되고 끄는 건 화면이 안 바뀌었습니다.
> 서버 상태 변경이 문제인지, response가 문제인지, DOM 변경이 문제인지 셋 다 가능해서, 코드를 바로 고치지 않고 Ajax `success`에서 response를 Console에 출력했습니다.
> 서버에서는 favorite 값이 true / false로 정상 반전되고 있어서, 서버 처리와 response까지는 정상이라고 보고 문제 범위를 JavaScript의 DOM 변경 쪽으로 좁혔습니다.
> 정확한 위치는 안내를 받아 확인했는데, false일 때 쓰는 class selector에서 점이 빠져 있었습니다.
> 수정한 뒤 양쪽 방향 모두 정상 동작하는 것을 실제 실행으로 확인했습니다.

### B. 문제 범위 좁히기 — 이번에 실제로 확인한 것

| 단계 | 이번에 확인한 방법 | 결과 |
| --- | --- | --- |
| request | (따로 확인하지 않음) | — |
| 서버 처리 | Console에 `response` 출력 | **정상** (`favorite` 반전됨) |
| response | 위 확인으로 함께 확인 | **정상** (`true / false`) |
| JavaScript → DOM | 남은 범위로 좁힘 | **여기가 문제** (`false`일 때 class selector `.` 누락) |

---

### C. 예상 꼬리질문 & 정직한 답변 방향

**Q1. 왜 코드부터 고치지 않았나요?**
→ 원인 후보가 세 개였는데, 어디가 문제인지 모른 채 고치면 무엇이 효과가 있었는지도 알 수 없다고 생각했습니다. response를 한 번 확인하면 서버 쪽 후보 두 개를 한꺼번에 정리할 수 있어서 그걸 먼저 했습니다.

**Q2. response에서 정확히 뭘 봤나요?**
→ `favorite` 값이 `true / false`로 정상적으로 반전되고 있는지를 봤습니다. 정상이어서 서버 상태 변경과 JSON response까지는 문제가 없다고 판단했습니다.

**Q3. 왜 한 방향만 안 됐나요?**
→ `false`일 때 사용하는 class selector에서 `.`이 빠져 있었습니다. `true` 쪽에서 쓰는 코드에는 문제가 없어서 켜는 방향은 정상 동작했습니다.

**Q4. 그 위치는 혼자 찾으셨나요?**
→ 아닙니다. 문제 범위를 JavaScript / DOM 쪽으로 좁힌 것까지는 직접 했고, `.`이 빠진 정확한 위치는 안내를 받아 확인했습니다.

**Q5. 같은 문제가 또 생기면 어떻게 하실 건가요?**
→ `request → 서버 처리 → response → JavaScript → DOM` 순서로 어디까지 정상인지 확인해서 범위를 줄이겠습니다.
