답: has - a

### 문제 8. 캡슐화와 프로퍼티
다음 코드에서 _price와 price의 역할을 설명한다.
```python
class Product:
    def __init__(self, price):
        self._price = price

    @property
    def price(self):
        return self._price

    @price.setter
    def price(self, new_price):
        if new_price < 0:
            raise ValueError("가격은 0원 이상이어야 합니다.")

        self._price = new_price
```
반드시 다음 내용을 포함한다.

- _price 앞의 밑줄이 뜻하는 관례
- @property의 역할
- setter를 사용하는 이유
- 잘못된 가격이 객체 내부에 저장되지 않게 되는 과정

답: 
_price 앞의 밑줄이 뜻하는 관례: instance의 속성에 대입되는 값이니 직접 건드리지말라는 관례
# 수정: 밑줄은 클래스 외부에서 직접 변경하지 말고 클래스 내부에서 관리하려는 속성이라는 관례
@property의 역할: def 함수이름():...의 함수이름을 변수처럼 보이게 하는 함수로 만드는 역할을 한다.
# 수정: getter method를 attibute에 접근하는 형태로 사용할 수 있게 한다.
setter를 사용하는 이유: 가격을 바꿀 때 검사를 하기 위하여
잘못된 가격이 객체 내부에 저장되지 않게 되는 과정: price의 setter가 실행되면 검사 과정을 거친 후 검사를 통과하면, 객체 내부에 저장된다.
# 수정: 잘못된 가격이 전달되면 ValueError가 발생하고, self._price = new_price까지 실행되지 않으므로 값이 저장되지 않는다.
# 보완: 현재 제시된 코드에서는 `__init__`이 `self._price = price`로 직접 저장하므로, 객체 생성 시에는 setter의 가격 검사를 거치지 않는다. 생성할 때도 같은 검사를 적용하려면 `self.price = price`로 작성해야 한다.

답: 자신의 클래스에 맞는 show_info()를 실행하기 때문이다.
# 수정: 실제 객체의 클래스에 정의된 메서드가 실행되기 떄문이다.
- 이것이 다형성과 어떤 관계가 있는가?

- 동적 디스패치란 무엇인가?

### 문제 3. 캡슐화와 다형성의 책임 차이

다음 두 코드의 차이를 설명합니다.
```python
#코드 A
if isinstance(product, DownloadProduct):
    if product.file_size < 0:
        raise ValueError("파일 크기가 잘못되었습니다.")
#코드 B
class DownloadProduct(Product):
    @property
    def file_size(self):
        return self._file_size

    @file_size.setter
    def file_size(self, value):
        if value < 0:
            raise ValueError("파일 크기가 잘못되었습니다.")

        self._file_size = value
```
다음 질문에 답합니다.

1. 코드 A에서는 누가 `DownloadProduct`의 값 검사를 책임지는가?
답: isinstance() 조건문
# 수정: 객체 외부의 호출 코드와 isinstance() 조건문
2. 코드 B에서는 누가 값 검사를 책임지는가?
답: @file_size.setter
# 수정: 클래스 내부의 file_size setter
3. 새로운 위치에서 `file_size`를 변경할 때 검사가 빠질 위험이 더 큰 방식은 어느 것인가?
답: isinstance() 조건문 방식
4. 코드 B가 캡슐화와 관련된 이유는 무엇인가?
답: 그 객체와 그 객체를 기능하게 하는 method를 한데 묶었으며, 특정 방식으로만 class에 접근할 수 있기 때문이다.
# 수정: _file_size라는 내부 상태와 그 값을 검사하는 규칙을 클래스 내부에 함께 묶어두고, file_size에 값을 대입할 때 setter를 거치게 하기 때문에 캡슐화와 관련된다.
5. 이 예제에서 다형성보다 캡슐화가 중심인 이유는 무엇인가?
답: file_size의 특정 조건을 만족해야지만 instance의 attribute에 접근할 수 있기 때문이다.
# 수정: 이 예제는 같은 메서드 호출이 객체 타입에 따라 다르게 동작하는 문제가 아니라 'file_size'에 잘못된 값이 저장되지 않도록 객체의 내부 상태를 보호나는 문제이므로 다형성보다 캡슐화가 중심이다.

**클래스와 객체**

- 클래스, 객체, 인스턴스의 차이를 확인했다.
- 인스턴스 속성과 클래스 속성의 차이를 확인했다.

- `Product`와 `DownloadProduct`처럼 공통 속성과 동작은 부모 클래스에 두고, 자식 클래스가 필요한 기능을 추가하거나 같은 메서드를 다시 구현했다.
- `super()`를 사용해 부모 클래스의 초기화 코드를 재사용했다.
- `is-a` 관계인 상속과 `has-a` 관계인 객체 구성을 구분했다.

**캡슐화와 다형성**

- 속성값을 외부에서 직접 변경하는 대신, 프로퍼티 setter에서 값을 검사하도록 해 캡슐화를 적용했다.
- 여러 상품 객체를 같은 방식으로 다루면서, 실제 객체의 타입에 따라 서로 다른 `show_info()`가 실행되는 다형성과 동적 디스패치를 확인했다.

**추상 클래스와 JSON**

- `ABC`와 `@abstractmethod`를 사용해 자식 클래스가 반드시 구현해야 하는 메서드를 정했다.
- 상품 객체를 JSON 파일에 저장한 뒤 다시 객체로 복원하는 과정까지 구현했다.

## 2. 이번 주에 구현한 프로그램

### 도서 관리 프로그램

클래스 기반으로 도서 등록, 전체 조회, 검색, 가격 변경, 삭제 기능을 구현했다. 이후 일반 도서, 전자책, 오디오북을 상속 구조로 나누고 자식 클래스마다 출력 동작을 다르게 만들었다.

### 상품 관리 프로그램

`Product`를 추상 클래스로 만들고 `NormalProduct`와 `DownloadProduct`가 이를 상속하도록 구성했다. 각 상품은 자신의 출력 방식과 딕셔너리 변환 방식을 직접 구현했다.

`ProductManager`는 상품 객체들을 리스트에 보관하고 다음 기능을 담당한다.

- 상품 추가
- 전체 조회
- 이름 검색
- 가격 변경
- 삭제
- JSON 저장
- JSON 불러오기

구현하면서 지킨 규칙은 세 가지다.

1. 전체 조회에서는 상품 종류를 `isinstance()` 조건문으로 나누지 않고, 각 객체의 `show_info()`를 호출했다.
2. 저장할 때는 각 객체의 `to_dict()`를 호출했다.
3. 불러올 때는 JSON의 `type` 값을 확인하여 알맞은 클래스 객체를 생성했다.

## 3. 처음 잘못 알고 있었던 부분 (면접 대비 정리)

### Q. 클래스, 객체, 인스턴스는 어떻게 다른가?

- 클래스는 객체가 가질 속성과 수행할 메서드를 정의한 설계도이다.
- 객체는 상태와 행동을 가지며 메모리에 실제로 존재하는 하나의 대상이다.
- 인스턴스는 특정 클래스를 바탕으로 실제로 생성된 객체이다.

처음에는 인스턴스를 클래스와 객체 사이의 연결처럼 설명했지만,
실제로는 특정 클래스로부터 생성된 객체 자체를 뜻한다.

### Q. 인스턴스에서 클래스 속성과 같은 이름에 값을 대입하면 어떻게 되나?

`product1`에 **같은 이름의 인스턴스 속성이 새로 만들어져서** 기존 클래스 속성을 가린다.

- `product1.category = "전자기기"`가 클래스 속성 자체를 바꾼다고 생각했는데, 그렇지 않다.

### Q. 프로퍼티 setter를 만들었는데 왜 생성 시점에는 검사가 안 되나?

생성자에서 `self._price = price`처럼 직접 저장하면 setter를 거치지 않기 때문이다. 생성 시점에도 검사를 적용하려면 **`self.price = price`** 를 사용해야 한다.

### Q. 추상 클래스는 왜 쓰나?

**자식 클래스가 반드시 구현해야 하는 메서드의 형식과 규칙을 강제**하기 위해서다.

- 단순히 공통 메서드를 모아두는 클래스라고만 생각했는데, 그게 핵심은 아니다.

### Q. `isinstance()`는 무조건 쓰면 안 되나?

항상 잘못된 것은 아니다. JSON 데이터를 실제 객체로 변환하는 것처럼 **구체적인 타입을 구분해야 하는 위치**에서는 사용할 수 있다.

- 다만 객체가 스스로 처리할 수 있는 출력 동작까지 외부 조건문으로 나누면, 새로운 타입이 추가될 때 수정할 코드가 많아진다.

## 4. 독립 재현 중 발생한 문제와 수정 과정

독립 재현에서 일반 상품과 다운로드 상품을 생성하고 조회, 검색, 가격 변경, 저장까지는 구현했다. 이후 세 가지 문제를 만났다.

### 문제 1. 저장한 JSON을 불러오면 상품 목록이 비어 있었다

처음 실행에서는 저장된 JSON 파일을 읽은 뒤에도 새로운 관리자 객체의 상품 목록이 비어 있었다.

`load()`의 실행 흐름을 다시 확인하면서 JSON에서 읽은 각 딕셔너리를
`create_product()`에 전달하고, 반환된 객체를 `self.products`에 추가하는 과정을 점검했다.

수정 후에는 저장된 딕셔너리가 각각 `NormalProduct`와
`DownloadProduct` 객체로 복원되고, 새로운 관리자 객체의 전체 조회에서도
두 상품이 정상적으로 출력되는 것을 확인했다.

### 문제 2. 불러오기에 실패해도 기존 상품이 그대로 남았다

없는 파일과 잘못된 JSON을 불러오는 테스트에서, 기존에 등록한 임시 상품이 그대로 남는 문제가 발생했다.

원인은 예외 처리에서 `return`만 실행한 것이었다. 반환값은 끝났지만 `self.products`의 기존 상태는 바뀌지 않았다.

`load()`가 시작될 때 먼저 목록을 비우도록 위치를 바꿔서 해결했다.

```python
self.products = []   # load() 시작 시점에 먼저 실행
```

이후 파일이 없거나 JSON 형식이 잘못된 경우에도 기존 상품 목록이 비워지고, 빈 상태로 시작하는 것을 확인했다.

### 문제 3. 가격 변경이 실패한 원인이 구분되지 않았다

처음에는 `ValueError`를 `update_price()` 내부에서 잡아 `False`로 바꾸었다. 이렇게 하면 상품이 없는 경우와 잘못된 가격인 경우가 똑같이 `False`로 보인다.

두 경우를 구분하기 위해, setter의 `ValueError`가 호출자에게 그대로 전달되도록 수정했다.

### 최종 확인 결과

| 상황 | 결과 |
| --- | --- |
| 정상 가격 변경 | `True` 반환 |
| 상품이 없을 때 | `False` 반환 |
| 음수 가격 입력 | `ValueError` 발생 |
| 저장 후 새 관리자 객체에서 불러오기 | 상품 복원 |
| 복원된 상품 삭제 | 성공 |
| 없는 파일 불러오기 | 빈 목록 |
| 잘못된 JSON 불러오기 | 빈 목록 |

## 5. 이번 주에 확인한 핵심 원칙

**1. 객체지향은 클래스를 쓰는 것이 아니라, 책임을 어디에 둘지 정하는 것이다.**

상품의 가격 검증은 관리자나 외부 조건문이 아니라 상품 객체 내부에서 책임지게 해야 한다. 상품별 출력 방식도 관리자에서 타입을 판별하기보다, 각 상품 클래스가 자신의 `show_info()`를 구현하도록 하는 편이 새로운 상품 종류를 추가하기 쉽다.

**2. 객체와 딕셔너리는 서로 변환해야 한다.**

JSON 파일에는 사용자 정의 객체를 그대로 저장할 수 없으므로 객체를 딕셔너리로 변환해야 한다. 반대로 JSON에서 읽은 딕셔너리는 메서드가 없는 단순 데이터이므로, 프로그램에서 사용하려면 다시 클래스 객체로 변환해야 한다.

**3. 값을 반환하는 것과 상태를 바꾸는 것은 다른 동작이다.**

`return []`을 작성했다고 해서 `self.products`가 자동으로 빈 리스트가 되는 것은 아니다.

## 6. 아직 부족한 부분

- 개념을 코드로 보고 구분하는 것은 가능하지만, 클래스·객체·인스턴스·캡슐화·다형성 같은 용어를 코드 없이 설명할 때 표현이 흔들린다.
- 상속과 객체 구성 중 어느 구조를 선택할지, 단순한 예제에서는 판단할 수 있지만 관계가 복잡해지면 기준을 바로 적용하기 어렵다.
- 독립 재현에서 주요 기능은 구현했지만, 예외가 발생했을 때 기존 객체 상태가 어떻게 남는지까지는 처음부터 고려하지 못했다. 정상 동작뿐 아니라 실패했을 때 프로그램의 상태가 어떻게 변해야 하는지도 설계 단계에서 확인할 필요가 있다.

---

## 7. 다음 복습에서 확인할 내용

- 객체지향 용어를 예제 없이 직접 설명해 본다.
- 두 클래스 사이의 관계를 보고 상속과 객체 구성 중 적절한 구조를 판단해 본다.
- 프로퍼티 setter가 객체 생성과 이후 변경 모두에서 실행되는지 확인한다.
- 새로운 자식 클래스를 추가했을 때 기존 관리자 코드의 수정 범위를 비교하여, 다형성이 실제로 어떤 부분의 변경을 줄이는지 다시 확인한다.
- JSON 저장과 불러오기에서 객체와 딕셔너리 사이의 변환을 처음부터 다시 작성한다.
- 파일 없음, 잘못된 JSON, 알 수 없는 상품 타입이 들어왔을 때 객체 목록의 상태가 어떻게 되어야 하는지 함께 점검한다.
